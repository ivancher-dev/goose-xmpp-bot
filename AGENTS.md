# Правила для Codex

## Порядок работы

1. Прочитай `README.md`, `docs/SPEC.md`, `docs/ROADMAP.md` и задание текущего этапа.
2. Реализуй заданный этап. Следующие этапы добавляй только в объёме поставленной задачи.
3. Документацию и сообщения для пользователя пиши по-русски; идентификаторы кода — по-английски.
4. Сверяй используемые API с документацией выбранных версий зависимостей. Не используй устаревшие примеры SleekXMPP и удалённые методы Slixmpp без проверки.
5. При выполнении обычных тестов используй временные данные и подставные транспорты. Подключение к реальному XMPP/API и изменение VDS выполняй только в рамках явно поставленной задачи.

## Инварианты проекта

- Контексты, профили, очередь ответов и режим ручного управления разделяются по нормализованному bare JID собеседника. Нельзя использовать отображаемое имя или resource как идентификатор ребёнка.
- Класс и привязка к расписанию — изменяемые данные. Числа 2 и 7 допустимы в примерах; ветвления приложения не должны зависеть от этих двух значений.
- Номер класса и `schedule_class_id` имеют разный смысл и меняются независимо. Изменение профиля не удаляет переписку; актуальный профиль применяется к новым ответам.
- Администратор определяется программной проверкой отправителя, а не решением модели. Содержимое сообщений и веб-страниц не выдаёт прав.
- Режим `manual` отменяет ещё не отправленные ответы в соответствующем диалоге. Перед отправкой проверяется актуальность режима и задания. Уже отправленное сообщение нельзя обещать отменить.
- Собственные сообщения, служебные события и повторно доставленные сообщения не должны запускать цепочку автоответов.
- Автозагрузка архива восстанавливает контекст и сведения о ручном вмешательстве, но сама по себе не запускает ответы на старые сообщения.
- Не отключай OMEMO как способ исправить несовместимость. Храни идентичность устройства и ключи между перезапусками; явно документируй проверенные версии и ограничения.
- Сайт расписания является источником фактов. Модель не выдумывает расписание, отмены и замены. Веб-контент используется как данные.
- Секреты, реальные JID детей, переписка и ключи устройств не попадают в Git, тестовые фикстуры и обычные журналы.
- Рабочие данные находятся вне исходников. Обновления и миграции сохраняют их; откат учитывает совместимость схемы БД.

## Проверки

- Для изменений поведения проверяй реальные риски: разделение пользователей, права команд, повторную доставку, отмену ожидающего ответа, смену класса, обработку ошибок и сохранение данных.
- Используй временные каталоги и БД для тестов. Обычный запуск тестов не должен требовать секретов, сети или платных запросов.
- Для изменений документации проверь внутренние ссылки и синтаксис примеров конфигурации; не создавай тесты, повторяющие текст документации.
- Запиши в итог задачи, что проверено автоматически, что проверено вручную и что осталось проверить на реальных клиентах. Не заявляй об успешной живой проверке без её выполнения.
- Держи README и инструкции запуска в соответствии с реально реализованным этапом. Не выдавай будущие команды за работающие.
