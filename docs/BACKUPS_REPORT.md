# Регулярные копии 0.3.4: проверки и ограничения

Дата: 29 октября 2026 года. Задание: [05b](tasks/05b-scheduled-backups.md),
установка и приёмка: [SCHEDULED_BACKUPS.md](SCHEDULED_BACKUPS.md).
Владелец выбрал ежедневные копии в 04:15 Europe/Moscow, хранение 14 копий.

## Реализовано

Online backup работающей SQLite без остановки Гуся, включая WAL. Сохраняются
конфигурация, env, образ и настройки обслуживания. Копия проходит проверку
хешей/прав/целостности и изолированное восстановление установленным приложением.
Только после этого она публикуется и запускается ротация. Копии перед
обновлением, повреждённые и чужие каталоги ротация не удаляет.

`goose-backup` предоставляет create/list/verify/restore-test/status и управление
таймером. По умолчанию 14 успешных копий, параметры меняются локальной командой.
Первая копия проверяется до включения таймера. Общая блокировка исключает
параллельное обслуживание обновлятором, не мешая рабочему data lock приложения.
Сеть в systemd-службе и проверяющем процессе запрещена; XMPP и модель не запускаются.

Схема SQLite остаётся 4, новые зависимости не добавлены. Рабочая OMEMO-база
никогда автоматически не подменяется прежним снимком.

## Автоматические проверки

Полный прогон: **522 теста прошли**, 292 upstream DeprecationWarning из
slixmpp-omemo. Дополнительно прошли `pip check`, сборка wheel 0.3.4,
компиляция Python, проверка shell/TOML/ссылок и `git diff --check`.

В `tests/test_backup.py` проверены:

- Копирование при удерживаемом приложением data lock и настоящем параллельном
  писателе SQLite в режимах DELETE/WAL; парные изменения одной транзакции
  остаются согласованными. Готовый снимок не требует WAL/SHM.
- Сохранение изменённого класса, независимых auto/manual, истории, города,
  записей OMEMO и внешних настроек. Права каталогов 0700, файлов 0600.
- Настоящий холодный запуск синтетической OMEMO-сессии из копии: прежняя
  идентичность и TRUSTED сохранены, следующий пакет расшифрован. Используется
  подставной PEP; соединений с настоящим XMPP нет.
- Пробный restore отдельного клона, запрет сети, неизменность исходной копии
  и рабочего хранилища. Старые копии обновлятора принимаются поддерживаемым форматом.
- Ограниченное ожидание занятой SQLite, недостаток места, сбой копирования/
  проверки, изменение настроек оператором и прерывание. Старые проверенные
  копии не удаляются ради неудавшейся попытки.
- Ротация только собственных проверенных снимков после новой успешной копии;
  защита update-*, чужих, неизвестных и повреждённых каталогов.
- Параллельный updater/backup, журнал прерванного обновления, лишние файлы,
  symlink, выход из каталога через manifest, неверные хеши/права/время.
- Включение таймера только после успешного restore; возврат его прежних
  настроек при отказе systemd, сохранение выключенного состояния при configure.
- Обновление автономных команд без замены пользовательских настроек и unit таймера.

`systemd-analyze calendar` принимает выбранное выражение с Europe/Moscow;
следующий ежедневный запуск соответствует 01:15 UTC, то есть 04:15 Москвы.
Рендер service/timer прошёл нативный `systemd-analyze verify`. Только ExecStart
при этой синтаксической проверке заменён доступным `/usr/bin/true`: системная
команда не установлена в облачном окружении. Это не запуск службы.

## Установленный wheel и разные UID

`tests/integration/check_backup_install.py` выполнен в одноразовом root-контейнере
Python 3.12 с отключённой сетью. Настоящий wheel установлен поверх тестового
0.3.3; зависимости взяты из ранее установленного тестового окружения.

Писатель UID 65534 непрерывно менял SQLite и держал data lock. Root-команда
создавала копии, выполняла реальный restore-test и ротацию до двух экземпляров,
не останавливая писателя. Проверены права, транзакционная согласованность,
профили и сохранение каталога update-*. Файл env с буквальным `$()` не исполнялся.
Checkout в `/root` намеренно отсутствовал — для копирования он не нужен.

Первый enable выполнен через entry point нового установленного пакета, когда
короткой команды ещё не было. Он зарегистрировал автономный goose-backup.
После временного удаления пути активного venv команды status/list/verify
продолжали работать. Повторная регистрация обновлятора сохранила настройки
и unit таймера и не вызвала никаких служб.

В этом контейнере systemctl/systemd-analyze подставные: проверены последовательность
и аргументы управления таймером, но не работа PID 1 и systemd sandbox.
Нативная проверка синтаксиса описана отдельно выше.

## Переход с уже установленного обновлятора 0.3.3

`tests/integration/check_backup_upgrade.py` успешно выполнен на отдельной
локальной установке из чистых коммитов. Сначала настоящий `install.sh --local`
установил 0.3.3 из e3dd59a вместе с его старой автономной командой goose-update.
Затем именно эта команда установила 0.3.4; новый updater до перехода не подменялся.
Git использовал локальный origin, pip — lock с проверкой хешей.

Проверена особенность первого перехода: старый работающий updater ещё не знает
о коротком goose-backup. Новый пакет уже содержит рабочий entry point;
первый enable через полный путь зарегистрировал автономную команду, создал
проверенную копию и локальные файлы таймера. Дополнительный create, verify
и restore-test успешно выполнены для обеих регулярных копий.

Повторное обновление уже новым updater сохранило байты настроек копирования
и unit таймера. SHA-256 конфига, env, пользовательского образа и рабочей SQLite
совпал до и после обоих обновлений. Подтверждены схема 4, изменённый класс,
независимые auto/manual, история, город и синтетическое состояние OMEMO.
Сохранены копии перед обновлениями, установленный `pip check` успешен.

Это локальный режим: systemd, XMPP и API не запускались. После финальной
правки синхронизации каталога снимка дополнительно прошли все 27 тестов
backup-модуля и повторная root-проверка окончательного wheel без сети.

Ручной `systemctl start` не подтверждает календарное срабатывание: оно остаётся
проверить после 31 октября, 04:15 МСК. Перезагрузка VDS, длительная ротация

требует отдельного выбора владельца и остановки всех экземпляров идентичности;
ограничения старых ratchet/prekey описаны в инструкции.

## Проверки восстановления в GitHub Actions

Владелец прислал журнал Actions с Python 3.12.15: 21 тест копирования упал
при пробном восстановлении, остальные 646 прошли. В тестовой установке путь
venv ссылался на `.venv` внутри checkout, тогда как workflow устанавливает
зависимости в Python из setup-python вне репозитория. Из-за отсутствия этого
каталога дочерний `doctor` не запускался; общий BackupError скрывал исходный
FileNotFoundError. Предупреждения slixmpp-omemo не были причиной отказов.

Сбой воспроизведён в отдельном чистом checkout без `.venv` при запуске внешним
Python 3.12.14. Исправлена только тестовая настройка: теперь она ссылается на
sys.prefix текущего pytest. Настоящие backup/restore и запрет сети продолжают
выполняться, проверки не отключались и не заменялись заглушками.

После изменения в таком checkout прошли все **667 тестов**, 296 upstream
предупреждений. В исходном checkout с обычной `.venv` отдельно прошли все
**27 тестов резервных копий**. Код приложения и версия 0.3.10 не менялись.
Повторный результат самого GitHub Actions после отправки исправления ещё
нужно подтвердить; локальная проверка не выдаётся за успешный удалённый запуск.
