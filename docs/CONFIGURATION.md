# Настройки и команды

Это проект интерфейса. До реализации соответствующего этапа команды ниже не являются работающими возможностями.

## Конфигурация приложения

Пример: [../config/config.example.toml](../config/config.example.toml). Реальная копия располагается вне Git, целевой путь — `/etc/goose-xmpp-bot/config.toml`.

В конфигурации задаются подключение XMPP, список разрешённых аккаунтов и администраторов, часовой пояс, включение модели и расписания, ограничения ресурсов и начальные профили. Неизвестные поля и неверные типы должны давать понятную ошибку; поля будущих этапов можно поддерживать как валидируемые неактивные настройки, но не игнорировать молча.

Секреты берутся из переменных `GOOSE_XMPP_PASSWORD` и `GOOSE_LLM_API_KEY`. Файл окружения на VDS имеет ограниченные права. Реальные секреты не передаются через сообщения боту.

Требования к валидации:

- TLS и проверка сертификата включены.
- Администраторы входят в allowlist; resource не меняет идентичность отправителя.
- Класс в начальной версии — целое число от 1 до 11; `academic_year` соответствует виду `YYYY-YYYY` с последовательными годами.
- Настроен существующий часовой пояс IANA.
- При включённой модели обязательны корректный HTTPS-адрес провайдера, модель и доступный секрет; при выключенной пустые значения допустимы.
- При включённом расписании обязателен настроенный источник; его работоспособность проверяется отдельно от синтаксиса.
- Каталог данных расположен вне исходников, доступен сервису и имеет подходящие права.
- `diagnostics.echo_enabled` по умолчанию выключен; даже при включении команда доступна только владельцу.

## Профили

Связка пользователя с классом хранится в SQLite. Начальные `users` из TOML используются для создания отсутствующих профилей; дальнейшие изменения базы не сбрасываются при перезапуске.

Два независимых поля:

| Поле | Пример изменения |
| --- | --- |
| `grade` | С 2 на 3 для уровня объяснений |
| `schedule_class_id` | Перепривязка к группе расписания, например после перехода в другую школу |

Отдельно меняется `academic_year`. Изменение этих полей не очищает память. Текущий профиль применяется при каждом новом запросе.

## Предлагаемый синтаксис команд

Все команды выполняются только от разрешённого отправителя. Префикс `!` позволяет посылать их обычным текстовым сообщением. Ответ на административную команду возвращается владельцу, а не в детский диалог.

| Команда | Кому доступна | Этап |
| --- | --- | --- |
| `!help` | Разрешённым пользователям | 1 |
| `!ping` | Разрешённым пользователям | 1 |
| `!echo <текст>` | Только владельцу на тестовом аккаунте, при явно включённой диагностике | 1 |
| `!admin status` | Владельцу | 1 |
| `!admin user show <bare_jid>` | Владельцу | 1 |
| `!admin user set <bare_jid> grade=3` | Владельцу | 1 |
| `!admin user set <bare_jid> academic_year=2027-2028` | Владельцу | 1 |
| `!admin user set <bare_jid> schedule_class_id=<id>` | Владельцу | 1 |
| `!admin mode <bare_jid> manual` | Владельцу | 2 |
| `!admin mode <bare_jid> auto` | Владельцу | 2 |
| `!context clear` | Пользователю для собственного контекста | 2 |
| `!schedule today` / `!schedule tomorrow` / `!schedule YYYY-MM-DD` | Пользователю для своего расписания | 4 |
| `!расписание сегодня` / `!расписание завтра` | Русские алиасы команды расписания | 4 |
| «Какие у меня завтра уроки?» | Пользователю, через проверенный инструмент | 4 |

Поле в `user set` выбирается из разрешённого списка; выражение не исполняется как Python, SQL или shell. Неизвестный пользователь и некорректное значение дают ошибку без частичного изменения профиля. Права проверяются программно до любых запросов к модели.

Для очистки через `!context clear` удаляются история и резюме именно отправителя. Справка объясняет, что очистка памяти бота не удаляет архивы на XMPP-сервере, устройствах и у провайдера.

## Начальные режимы

На первом этапе модель отключена. На втором и последующих новый диалог создаётся в `manual`. Сохранённый режим имеет приоритет над `default_mode`; конфигурация не включает автоматически уже поставленный на паузу разговор.

Автоматический перехват по ручному исходящему сообщению появляется на этапе 3. Он ставит только этот диалог в `manual`. Возврат выполняется командой владельца; календарного таймера возврата по умолчанию нет.

## Диагностика

`doctor.sh` должен разделять проверки:

- По умолчанию: локальные версии, синтаксис конфигурации, права, доступность каталога данных и состояние сервиса.
- Явная XMPP-проверка: реальная авторизация тестовой учётной записи, TLS и обнаружение поддерживаемых расширений. При возможном конфликте с работающим ресурсом сообщает о нём и использует отдельный диагностический resource; проверка не регистрирует новое OMEMO-устройство.
- Явная API-проверка после этапа 2: отдельный выбранный режим; сообщает, что запрос может тарифицироваться. Обычная диагностика запрос модели не делает.

Вывод не содержит секретов, полного содержимого сообщений, ключей устройств и приватных промптов.
