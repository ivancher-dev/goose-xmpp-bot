# Отчёт по реализации этапа 1

Исходная реализация: 21 октября 2026 года; обновлено 23 октября 2026 года. Реализован диагностический сервис; живая клиентская приёмка выполняется, полный набор сценариев ещё не пройден.

## Решения

Python 3.12; Slixmpp **1.17.0**, slixmpp-omemo **2.2.0**, OMEMO/Oldmemo/Twomemo **2.1.0**. Прямые и транзитивные зависимости, backend сборки и SHA-256 зафиксированы в `requirements.lock`, тестовые — в `requirements-dev.lock`. Один `asyncio`-цикл, ограниченная последовательная очередь; SQLite-операции выполняются через `asyncio.to_thread`, а не в цикле транспорта.

Публичные API сверены с опубликованными исходниками выбранных пакетов и официальной документацией в репозитории slixmpp-omemo:

- [Getting Started](https://github.com/Syndace/slixmpp-omemo/blob/b77bdd4cc16702a74bdaf23bdf543499f2f30515/docs/getting_started.rst): подкласс XEP_0384, Storage, hooks ручного доверия.
- [Официальный пример](https://github.com/Syndace/slixmpp-omemo/blob/b77bdd4cc16702a74bdaf23bdf543499f2f30515/examples/echo_client.py): `get_session_manager`, `encrypt_message`, `decrypt_message`, `is_encrypted`, регистрация плагина. BTBV, синхронный JSON и открытые ответы на ошибки из примера не перенесены.
- [XEP_0384 2.2.0](https://github.com/Syndace/slixmpp-omemo/blob/b77bdd4cc16702a74bdaf23bdf543499f2f30515/slixmpp_omemo/xep_0384.py): ограничения SCE, lifecycle, контракт storage и криптографии.
- [Документация Slixmpp](https://slixmpp.readthedocs.io/en/latest/): `ClientXMPP.connect()` возвращает Future, `disconnect()` ожидается; удалённый старый `process()` не используется. Собственный код обращается к плагинам через `.plugin`.
- [PyOMEMO API](https://py-omemo.readthedocs.io/en/latest/omemo/session_manager.html): `create`, `shutdown`, `get_device_information`, `set_trust`, `format_identity_key`. Контракты дополнительно проверены тестами с реальными ключами.

ReadTheDocs из этой облачной среды возвращал 403, поэтому документация плагина прочитана из официального Git-репозитория, а точные сигнатуры сверены с установленными пакетами. Выбранная версия плагина ещё сама использует устаревающее `xmpp[...]`: тесты показывают DeprecationWarning из зависимости, это не пропущенные проверки и не подавленная ошибка.

## Реализовано

- Строгий TOML: типы, неизвестные поля, JID, права, профили, IANA timezone, обязательные TLS/OMEMO, запрещённое включение будущих функций. Пароль только из окружения, без вывода значения.
- SQLite со схемой и привязкой к аккаунту; начальные профили вставляются только при отсутствии. Изменение класса/года/группы независимо и сохраняется при повторной загрузке.
- Диагностические команды, разрешённые поля, проверка администратора до доступа к профилям, opt-in echo только владельцу. Свободный текст не запускает ответы.
- Проверка входящих Carbons с нормализацией внутреннего сообщения; общая дедупликация с прямой доставкой. Фильтрация собственных сообщений, исходящих/поддельных Carbons, MAM, остальных forwarded/delayed, квитанций и служебных событий. Ограниченные подключения.
- Постоянные ключи, ratchet-сессии и ручное доверие, CLI для сверки отпечатка и отзыва. Ошибки шифрования/доверия блокируют ответ без открытого fallback.
- Установщик с отдельным пользователем, virtualenv, сохранением конфигурации/данных, без автоматического старта по умолчанию; systemd unit; локальный doctor и явная сетевая диагностика без OMEMO-идентичности.

## Проверки

Автоматические офлайн-проверки охватывают ошибки конфигурации, нормализацию JID, разделение и сохранение профилей, права и некорректные аргументы, выключенное echo и буквальный текст shell-выражений, блокировку второго процесса, дедупликацию, обработку оболочек, ограничение очереди, TLS-настройки, отказ при отсутствующем пароле и ограниченные повторы.

Отдельно используется настоящая криптография Oldmemo: обмен, запрет отправки без ручного доверия, несовпадение отпечатка, отзыв доверия, сохранение ID/ключа/доверия/ratchet после повторного открытия SQLite. Интеграционный офлайн-тест через настоящий XML API плагина проверяет `!ping` → зашифрованный `pong` и отсутствие повторного ответа. Сетевые вызовы в обычных тестах запрещены.

В облачной среде Python 3.12.14 выполнены 87 офлайн-тестов: все прошли, пропусков и ожидаемых ошибок нет. В зависимости остаются 23 предупреждения DeprecationWarning. Прошли `pip check`, компиляция Python, `bash -n`, проверка локальных ссылок документации и TOML, `git diff --check`.

Установщик дважды выполнен с `--local` из чистого checkout: настоящая установка пакета и зависимостей с проверкой хешей, повторное сохранение изменённого конфига, env и SQLite побайтно, проверка изменённого профиля и синтетической записи OMEMO. Сгенерированный unit прошёл `systemd-analyze verify`; установленная CLI и `doctor.sh` проверены. Эти проверки не запускают реальный systemd/XMPP.

Эти облачные проверки не охватывали реальный systemd, установку от root на VDS, Gajim/Conversations, маршрутизацию и измерения ресурсов. Позднейшие ручные наблюдения владельца приведены ниже; сценарии находятся в [TESTING_XMPP.md](TESTING_XMPP.md).

## Исправление маршрутизации, 23 октября 2026 года

При ручной проверке владельцем команда появилась в другом клиенте тестового аккаунта, а сервис сообщил `message_ignored reason=carbon`. Причина в реализации: отрицательный приоритет исключал сервис из bare-доставки, а фильтрация всех Carbons отбрасывала и живые входящие копии. Полная клиентская приёмка по-прежнему не завершена.

Теперь постоянный сервис объявляет приоритет `0` и принимает проверенные `received`-копии. Внешний отправитель должен точно совпадать с bare JID аккаунта; проверяются структура и получатель, а внутренний отправитель и его устройство проходят обычную авторизацию и OMEMO. Архив, задержанные, исходящие, вложенные и поддельные копии отбрасываются. Команды управления устройствами и диагностика остаются с приоритетом `-1`, без обработчика команд. Схема БД, ключи и решения доверия не меняются.

Офлайн-тест с настоящим XML API OMEMO проверяет оба порядка: Carbon → прямая доставка и прямая доставка → Carbon. В каждом случае получается один зашифрованный `pong`. Дополнительно проверены подделки отправителя/получателя, некорректная структура, вложенные оболочки, архив/delay, allowlist внутреннего отправителя и приоритеты трёх режимов. Общий прогон: **127 тестов прошли**, 36 предупреждений DeprecationWarning из slixmpp-omemo. Прошли `pip check`, компиляция Python, `bash -n`, проверка локальных ссылок/TOML и `git diff --check`.

После установки `03acc48` на VDS владелец подтвердил получение зашифрованного `pong` в Gajim **2.4.6 на Windows**. Использованы включённый OMEMO в чате и ручное доверие также к другим устройствам самого аккаунта бота. Журнал показал прямую доставку, постановку ответа на отправку и отбрасывание исходящих Carbons/квитанции; получение подтвердил клиент. Это подтверждает один сценарий legacy OMEMO, но не весь план приёмки. Conversations, входящий `received-carbon`, full JID, обрыв связи и остальные сценарии остаются открытыми. Подробности без реальных JID и отпечатков записаны в [TESTING_XMPP.md](TESTING_XMPP.md).

## Ограничения

Поддержан только legacy namespace `eu.siacs.conversations.axolotl`. В slixmpp-omemo 2.2.0 есть backend OMEMO 2 и его публикация при инициализации, но отправка SCE не реализована, а расшифровка SCE заканчивается `NotImplementedError`. Это известное ограничение выбранной зависимости: сервис отбрасывает неподдерживаемые сообщения и не переходит на открытый текст. Если фактические клиенты работают только с `urn:xmpp:omemo:2`, эта версия не подходит; нужно отдельное исправление/обновление интеграции и повторная приёмка. Взаимная совместимость обоих клиентов не заявляется.

Полная история, автоматическая пауза, генерация, расписание, безопасное обновление/откат, основной аккаунт и ресурсные лимиты не реализуются в этом этапе. Подробные эксплуатационные ограничения доставки и хранения указаны в [INSTALLATION.md](INSTALLATION.md).
