# Проверки обновления и автозапуска 0.3.3

Дата: 28 октября 2026 года. [Инструкция](SAFE_UPDATES.md),
[задание](tasks/05a-safe-updates.md).

## Что реализовано

Однократный `setup-updater.sh` регистрирует автономную команду на системном
Python 3.12 поверх прежней установки. Свежий `install.sh` тоже её регистрирует.
Обычный `sudo goose-update` фиксирует SHA main и готовит отдельный venv
с проверкой хешей зависимостей до остановки сервиса. Затем идут блокировка,
проверенная частная копия, пробная миграция отдельного клона, переключение,
готовность нового XMPP-процесса и включение службы при загрузке ОС.

Автоматический возврат касается только кода/unit и требует прежней схемы,
совпадающих версий runtime-зависимостей и успешного старого doctor.
Действующая база и OMEMO-состояние никогда не заменяются старой копией.
Журнал обнаруживает прерванную операцию, `--recover` выполняет отдельную
проверенную попытку возврата. `--check` только готовит версию.

Сохранённый auto восстанавливается при полном MAM с Carbons. Временный отказ
не теряет подтверждённый anchor; следующий успешный poll снимает паузу.
Неудавшийся discovery MAM повторяется. Утраченная позиция требует подтверждения,
намеренный manual и новые manual-профили не включаются автоматически.

Появились `Type=notify`, автоповтор через 30 секунд и разные коды завершения:
75 для временного сбоя, 2 для ошибок настроек, авторизации или ключей.
Распознаются также сетевые IQ/OMEMO-обёртки, без разбора текста исключений.
После частичной инициализации OMEMO повтор выполняется новым процессом.
doctor/maintenance не уведомляют systemd о готовности рабочего бота.

## Автоматические проверки

Общий прогон: **475 тестов прошли**, 254 upstream DeprecationWarning из
slixmpp-omemo. Обычные тесты не используют XMPP, API, ключи или реальные JID.
Прошли `pip check`, компиляция Python, `bash -n` всех установочных скриптов,
проверка unit через `systemd-analyze verify`, TOML-примеры, ссылки и diff.
Шаблон проверяется с доступным тестовым executable; служба в облаке не запускалась.

На временном диске и подставном systemd проверены:

- Успешное переключение прежнего каталога на symlink, приватная копия с хешами,
  сохранность внешних настроек/образа и исходной базы.
- Отказы загрузки, копирования, пробной миграции, переключения и готовности.
  До подготовки нет остановки; после совместимого возврата остаётся старый код.
- Изменившийся после запуска ratchet сохраняется при возврате кода.
  Изменение схемы или зависимостей запрещает автоматический откат и оставляет
  новые данные и журнал для диагностики.
- Прерывание между переносом legacy-каталога и созданием ссылки; отдельный
  recover восстанавливает путь без старой базы.
- Параллельное обновление, занятый data lock, грязный checkout, смена настроек
  во время подготовки, неподходящий ref и символические ссылки в данных.
- Пробная миграция получает отдельный клон; исходные данные и сохранённая
  копия не становятся объектом её записи.
- Очистка подготовленных окружений сохраняет активный release; команда
  и entry point остаются читаемыми и исполняемыми для пользователя службы.
- Настоящий UNIX datagram `READY=1` без личных данных; старый InvocationID,
  `Type=simple` и ещё запускающийся процесс не считаются готовым обновлением.
- Уведомление готовности не приходит до завершения начальной MAM-проверки.
  Временный timeout сохраняет anchor и допускает auto только после повтора;
  manual другого диалога и потерянный anchor не обходятся этим восстановлением.
- Различение временной ошибки и неверной авторизации/конфигурации в CLI;
  временная инициализация OMEMO требует закрытия клиента и нового процесса.

Проверка настоящей установки отдельно обнаружила ошибку подстановки пути
в автономный launcher; она исправлена, скомпилированный launcher включён в тест.
Также отдельно проверены права executable после сборки под umask 0077.

## Настоящие установленные пакеты

В отдельном каталоге из чистых коммитов проверен путь установленного wheel
0.3.2 → подключение команды → `--check` → 0.3.3 → повторное обновление 0.3.3.
Git использовал локальный origin; pip загружал зафиксированные зависимости
обычным HTTPS с проверкой хешей. XMPP, API модели и systemd не запускались.

При подключении команды старое окружение и данные не менялись. После обеих
активаций SHA-256 конфигурации, env, пользовательского образа и SQLite
совпали с исходными. Проверены схема 4, изменённый профиль, независимые auto/
manual, история, сохранённый город, синтетическая запись OMEMO и подтверждённый
anchor. Копии имели правильные хеши и приватные права; сохранены два release.
Версия установленного CLI — 0.3.3, `pip check` успешен, entry point исполняем
для пользователя службы.

На установленном wheel отдельно подставлен отказ готовности: выполнен возврат
к предыдущему окружению без замены рабочей SQLite, журнал завершён. Ещё одна
настоящая свежая установка 0.3.3 через `install.sh --local` зарегистрировала
исправный автономный launcher; локальный doctor не создал БД/идентичность.

После этой проверки дополнительно закрыта гонка ручной правки конфига/env/unit
во время пробной миграции: перед переключением повторно сверяются хеши,
обновление отменяется и правки оператора сохраняются. Эти случаи проверены
на временном диске тестами с инъекцией отказа.

## Что остаётся проверить на VDS

Живую приёмку 0.3.3 владелец ещё не выполнял. Нужны первое подключение команды,
обновление, новый свободный вопрос в прежнем auto, сохранение manual и
перезапуск только службы с успешным MAM. Работа реальных Gajim/Conversations
с 0.3.2 подтверждена ранее, но не подменяет приёмку этого обновлятора.

Перезагрузка VDS не выполнялась и отложена владельцем. Запуск после загрузки
пока подтверждается конфигурацией systemd и моделью отказов, без живого reboot.
Нет утверждения об успешном реальном сетевом обрыве или отказе диска на VDS.

Регулярное копирование по таймеру, ротация, внешнее хранение и восстановление
из копии — следующая задача. Резервные копии перед обновлением сохраняются
без автоматического удаления. Рабочую OMEMO-базу нельзя безусловно откатывать
даже при наличии проверенной копии.
