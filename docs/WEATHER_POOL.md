# Пять погодных источников, 0.3.15

Гусь перебирает источники последовательно и использует первый пригодный прогноз.
Усреднения между сервисами нет. [Команды уведомлений](WEATHER_ALERTS.md) прежние:
город и количество/время сводок задаются в чате, время относится к городу,
рассылка работает и в manual.

| Идентификатор | Сервис | Доступ и особенности |
| --- | --- | --- |
| `yandex` | Яндекс Погода, Россия | Бесплатный личный ключ «Для умного дома», сегодня/завтра; 30 запросов в сутки и 1000 в месяц |
| `wttr` | wttr.in | Без ключа; прежний адаптер WWO JSON |
| `open_meteo` | Open-Meteo | Без ключа; прежний прогноз и поиск городов |
| `met_no` | MET Norway Locationforecast | Без ключа, глобальный прогноз; атрибуция CC BY 4.0, HTTP-кэш по условиям сервиса |
| `seven_timer` | 7Timer! CIVIL | Без ключа, глобальная модель GFS; интервалы 3 часа, ветер передаётся категориями |

Контракты и условия сверены с [первичными источниками](WEATHER_POOL_REPORT.md).
Несколько API могут использовать общие исходные модели. Точность для конкретного
города и доступность с VDS требуют наблюдения; география проекта не гарантирует
расположение его серверов или прохождение сетевых блокировок.

## Порядок и таймауты

Прежний `weather.provider` остаётся первым. Если `fallback_providers` отсутствует,
добавляются остальные в порядке `yandex`, `wttr`, `open_meteo`, `met_no`, `seven_timer`,
без повтора основного. Например, для прежнего `wttr`:
`wttr → yandex → open_meteo → met_no → seven_timer`.
Без ключа Яндекс пропускается сразу; остаются четыре сервиса.

Если в действующем конфиге уже есть `fallback_providers = ["open_meteo"]`,
обновление сохранит именно этот список. Для расширения его нужно заменить
или удалить поле, чтобы заработал автоматический резерв.

Пример с российским основным источником после получения ключа:

```toml
[weather]
enabled = true
provider = "yandex"
fallback_providers = ["wttr", "open_meteo", "met_no", "seven_timer"]
yandex_api_key_env = "GOOSE_YANDEX_WEATHER_KEY"
```

Допустимы до четырёх резервных источников без повторов; `[]` отключает резерв.
Не добавляйте вторую таблицу `[weather]`: измените существующую.
Каждый источник получает до 4 секунд, весь пул — до 22 секунд. Интерактивное
задание имеет общий срок 40 секунд, включая очередь и поиск города.
Уведомление ждёт свободного места в пределах своего прежнего окна 10 минут;
после получения места имеет 35 секунд на прогноз, подготовку и отправку.
Ожидание места больше не расходует этот рабочий бюджет.

Таймаут, HTTP/сетевая ошибка, превышение размера и непригодные данные запускают
следующий источник. Отказавший сервис уступает здоровым на 120 секунд,
но остаётся последним шансом, если отказали и они. В журнале:
`weather_source_failed provider=… reason=timeout|http_status|network|data status=…`.
Пропуск Яндекса: `weather_source_skipped provider=yandex reason=unconfigured|configuration|quota|quota_storage`.
Причины не содержат ответа API, ключа, города или JID.

## Личный ключ Яндекса

1. Получите **личный** бесплатный ключ [«Для умного дома»](https://yandex.ru/pogoda/b2b/smarthome).
   У бизнес-тарифов другие условия. Сам ключ не отправляйте в чат и не коммитьте.
2. На VDS откройте существующий защищённый файл:

```bash
sudoedit /etc/goose-xmpp-bot/goose.env
```

Добавьте строку `GOOSE_YANDEX_WEATHER_KEY="ВАШ_ЛИЧНЫЙ_КЛЮЧ"`, сохранив остальные
переменные. В TOML хранится только имя переменной.
3. После слияния обновления в main выполните `sudo goose-update`. Если 0.3.15
   уже установлена, после изменения env/config нужен `sudo systemctl restart goose-xmpp-bot`.
   До слияния можно установить проверенный SHA через `goose-update --ref SHA`.
4. Проверьте `!weather`, `!weather tomorrow` и строку источника. Если Яндекс
   остаётся резервным, до него дойдёт очередь только при отказе основного.

Ключ отправляется только заголовком HTTPS-запроса Яндексу, без перенаправлений.
Данные Яндекса не кэшируются. SQLite хранит только времена попыток: максимум
30 за скользящие 24 часа, включая ошибки, с сохранением после перезапуска.
Этот предел также укладывается в 1000 запросов за календарный месяц.
При исчерпании бот сразу переходит к резерву. Лимит локален для этой установки;
если тот же ключ используется другими приложениями, они расходуют общую квоту.
Запросы погоды не входят в статистику токенов модели.

## Данные и ограничения

У MET Norway используется идентифицирующий User-Agent, округление координат
до четырёх знаков, `Expires`/`Last-Modified`/условный GET и безопасное перенаправление
только внутри того же HTTPS-хоста. Другие сервисы не получают ключ Яндекса.
Обычный кэш Open-Meteo, wttr.in и 7Timer! — до пяти минут; после ошибки данных
ответ удаляется. Просроченный ответ не заменяет свежий.

У новых адаптеров временные метки обязаны содержать часовой пояс; прогноз
выбирается по суткам города. MET Norway и 7Timer! старше 12 часов не принимаются,
время ответа Яндекса — не старше 15 минут; будущее более чем на 5 минут отклоняется.
Проверяются покрытие нужного дня, пропуски более 3 часов, дубликаты,
единицы и диапазоны. MET Norway также возвращает проверяемые координаты точки.

MET Norway и 7Timer! не выдаются за текущее наблюдение. Для новых адаптеров
минимум/максимум подписаны «По доступным интервалам HH:MM–HH:MM»; это могут быть
только оставшиеся часы сегодня. Отсутствующая вероятность осадков не становится
нулём. Категория ветра 7Timer! показывается диапазоном, например 3,4–8 м/с,
и не используется как точное число для совета о шапке.

Общая сеть VDS и поиск **нового** города/его timezone по-прежнему общие точки отказа.
Сохранённому городу с timezone геокодер для прогноза не нужен. При полном отказе
пула уведомление может сообщить недоступность без выдуманных цифр. Прежняя
защита от повторов отмечает попытку до получения прогноза; бесконечных повторов нет.

Схема SQLite остаётся 8, зависимости прежние, подписки и данные сохраняются.
[Проверки и живая приёмка](WEATHER_POOL_REPORT.md).
