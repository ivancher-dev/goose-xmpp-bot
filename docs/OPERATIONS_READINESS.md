## Первый сбор состояния на VDS

Команды только читают состояние: не меняют настройки, не перезапускают службы,
не вызывают модель и не печатают конфигурацию, переписку или ключи.

```bash
sudo systemctl show goose-xmpp-bot.service --property=ActiveState,SubState,UnitFileState,NRestarts,Result,MemoryCurrent,MemoryPeak,TasksCurrent,ActiveEnterTimestamp
sudo goose-backup status
free -h
df -h /var/lib/goose-xmpp-bot /var/backups/goose-xmpp-bot
```

Проверяем active/running, автозапуск, количество и контекст перезапусков,
память процесса и доступную память хоста, запас на обоих путях диска.
Показатель MemoryCurrent относится к cgroup службы, а не только RSS Python.
В выводе копирования нужны свежесть последнего успеха, restore_checked,
состояние таймера и результат последнего системного запуска. Сам по себе
успешный запуск службы не отличает ручной старт от календарного; для приёмки
календаря нужны согласованные время запуска, расписание и свидетельство таймера.

После первых результатов при необходимости отдельно:

```bash
sudo /opt/goose-xmpp-bot/venv/bin/goose-bot doctor --config /etc/goose-xmpp-bot/config.toml
sudo goose-backup list
sudo systemctl show goose-xmpp-bot-backup.timer --property=ActiveState,UnitFileState,LastTriggerUSec,NextElapseUSecRealtime
sudo du -sh /var/lib/goose-xmpp-bot /var/backups/goose-xmpp-bot /opt/goose-xmpp-bot/releases
```

Локальный doctor проверяет TOML, права, целостность и схему SQLite в read-only,
не подключаясь к XMPP/API. Отсутствующий в процессе doctor пароль или API-ключ
сам по себе не означает отсутствие секрета у systemd: окружения различаются.
Для проверки копии использовать конкретный путь из `goose-backup list` и
`goose-backup restore-test <путь>`: он работает с отдельным временным клоном.
Клону нельзя давать рабочее XMPP-подключение или запускать вторую активную
идентичность OMEMO. Перед восстановлением большого клона проверить свободное место.

   запуск таймера, свежая копия и пробное восстановление подтверждены.

   проверить фактическую ротацию при достижении 14 успешных копий.
3. Владелец указал домашний компьютер Windows 11 как доступное внешнее хранилище,
   на VDS входит по SSH как root. Подготовлена [инструкция скачивания и проверки
   SHA256](WINDOWS_BACKUPS.md). План — забирать проверенную копию с компьютера, когда
   он включён; постоянно включённый домашний сервер не предполагается.
   Копия на другом каталоге того же VDS не независима.
   Копии содержат env, ключи и память; нужны приватный доступ/шифрование и доступный
   владельцу способ расшифрования при потере VDS. Способ передачи, получатель,
   ключ и внешняя ротация определяются перед настройкой; загрузка пока не выполнялась.
4. Измерить ресурсы и рост данных на обычном интервале работы; сравнить повторную
   сводку службы/копий и расход API. Пороговые ограничения выбирать по этим данным.
5. Завершить клиентские сценарии и проверить восстановление после обрыва/перезапуска
   в согласованное окно. Полная перезагрузка VDS, принудительное падение и замена
   рабочей БД требуют отдельного выбора владельца и не входят в сбор состояния.

Рабочую OMEMO-базу автоматически из старой копии не подменять. Наличие старого
wheel не даёт совместимого отката после миграции схемы. Для уже установленной
схемы 8 старый код схемы 7 непригоден как прямой откат.
