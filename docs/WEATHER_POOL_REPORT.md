# Пул пяти источников: выбор и проверка 0.3.15

Запрос и согласование ключа: 05.11.2026. [Задание](tasks/02c-weather-provider-pool.md),
[установка и параметры](WEATHER_POOL.md).

## Почему эти сервисы

В пул добавлены три адаптера к прежним Open-Meteo и wttr.in. Это разные HTTP-сервисы,
но не обещание пяти независимых метеомоделей или одинаковой точности.

- **Яндекс Погода** — российский источник с широким покрытием. Выбран именно
  бесплатный личный [тариф «Для умного дома»](https://yandex.ru/pogoda/b2b/smarthome),
  а не бизнес API: сегодня/завтра, 30 запросов в сутки, 1000 в месяц.
  [Личные условия](https://yandex.ru/legal/apib2c_weather_agreement/ru/).
  GraphQL-запрос, POST, заголовок и поля сверены с
  [официальной интеграцией Яндекса](https://github.com/yandex/pogoda-home-assistant/blob/main/custom_components/yandex_pogoda/updater.py)
  и [именами полей/условий](https://github.com/yandex/pogoda-home-assistant/blob/main/custom_components/yandex_pogoda/const.py).
  Ключ получает владелец; код его не содержит. Данные не кэшируются,
  только времена попыток сохраняются для локального лимита.
- **MET Norway Locationforecast 2.0 compact** — глобальный прогноз, вне Северной
  Европы использует ECMWF. [Модель данных](https://docs.api.met.no/doc/locationforecast/datamodel),
  [ForecastJSON](https://docs.api.met.no/doc/ForecastJSON.html),
  [условия доступа](https://docs.api.met.no/doc/TermsOfService).
  Учтены User-Agent с контактом проекта, координаты до четырёх знаков,
  сжатие, HTTP-кэш, условные запросы и CC BY 4.0.
- **7Timer! CIVIL** — проект китайского происхождения, глобальный прогноз на GFS.
  [Документация](https://www.7timer.info/doc.php?lang=en),
  [актуальная wiki проекта](https://github.com/Yeqzids/7timer-issues/wiki/Wiki).
  Выбран CIVIL с UTC-началом и часовыми смещениями: местные сутки определяет бот,
  без предположений о дате продукта CIVILlight. Категории ветра переводятся
  в диапазоны, точное значение и вероятность осадков не выдумываются.
- Прежние [Open-Meteo](https://open-meteo.com/en/docs) и
  [wttr.in JSON](https://github.com/chubin/wttr.in#json-output) сохранены;
  явные настройки владельца не расширяются скрытно.

Другие российские кандидаты не добавлены автоматически:
[Gismeteo API](https://docs.gismeteo.net/v3/weather) требует отдельного доступа,
рабочий бесплатный контракт для этой установки не подтверждён;
[rp5 XML](https://rp5.ru/docs/xml/ru) требует регистрации получателя/IP и точек;
старые XML-выгрузки Meteoservice в сессии подтвердить не удалось.
Это не оценка точности этих прогнозов. Чужие ключи, закрытые запросы сайтов
и HTML-парсинг для обхода доступа не используются.

## Изменение поведения

При непригодном ответе или таймауте идёт следующий источник, без усреднения.
Бюджеты: 4 секунды на источник / 22 на пул / 40 на интерактивное задание.
Уведомление получает 35 секунд после ожидания свободного места, в пределах
прежнего окна 10 минут. Это закрывает сценарий, когда очередь расходовала
время до начала получения прогноза. Причину отдельных пропусков на VDS
по имеющимся сведениям однозначно установить нельзя.

Сохраняются ручные режимы, подписки, защита от повторов и отмена устаревшего
задания. Схема БД 8 и зависимости не менялись. Новое состояние квоты —
одна служебная запись с максимум 30 временными метками, без ключа и прогноза.

## Проверки

Полный офлайн-прогон: **844 теста прошли**. Проверки зависимостей `pip check`,
компиляции Python, синтаксиса shell/TOML, внутренних ссылок изменённых инструкций
и `git diff --check` прошли. Установленное обновление проверяется отдельно.
Основные сценарии: отказ первых четырёх источников,
таймауты до последнего, четыре сервиса без ключа, неправильный JSON/GraphQL,
неполный день, старые/будущие метки, координаты/единицы, UTC и местная полночь,
кэш/304/gzip/перенаправления MET, квота после открытия БД, отсутствие утечки
заголовка ключа и ожидание очереди уведомлений.

## Что осталось на VDS

В этой сессии реальные XMPP и погодные API с VDS не вызывались. Сетевой доступ
среды разработки к выбранным погодным API ограничен; контрактные проверки
используют синтетические ответы и MockTransport. Отсутствие блокировки или
точность прогноза для города этим не доказаны.

После установки и добавления ключа:

1. Проверить сегодня/завтра и источник ответа, отдельно — Яндекс.
2. Подтвердить доступ каждого сервиса с VDS, временно оставляя его единственным
   через `provider` и `fallback_providers = []`; затем вернуть полный пул.
   Не отключать TLS и не менять firewall ради искусственных отказов.
3. Получить сводку по расписанию в manual, сверить часы/город и отсутствие
   повтора после перезапуска. При проблеме смотреть безопасные причины в журнале.
4. Несколько дней сопоставлять прогноз с наблюдением в городе. Только после
   этого выбирать основной по точности и доступности; исходный порядок не
   является рейтингом точности.

Общая сеть, геокодер нового города, неготовый XMPP, недоверенное OMEMO-устройство
и прежняя отметка попытки до отправки остаются ограничениями. Резерв API
уменьшает число отказов сервиса, но не гарантирует доставку каждой сводки.
