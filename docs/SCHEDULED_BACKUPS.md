# Регулярные копии Гуся, 0.3.4

[Задание](tasks/05b-scheduled-backups.md), [результаты проверок](BACKUPS_REPORT.md).
Выбранный владельцем режим: **ежедневно в 04:15 Europe/Moscow, хранить 14 копий**.
Это локальные копии на том же VDS. Внешнее хранилище в этот этап не входит.

## Что сохраняется

SQLite копируется штатным online backup API: получается согласованный снимок
зафиксированных транзакций, включая режим WAL. Обычный Гусь продолжает работать.
Профили, режимы, история, города, идентичность/ключи OMEMO и доверие находятся
в этой SQLite. Результат преобразуется в самодостаточную базу без WAL/SHM.
Дополнительно копируются конфиг, env, внешний образ, unit и настройки обслуживания.

Копия сначала пишется во временный приватный каталог. Проверяются SHA-256,
целостность SQLite, затем выполняется пробное восстановление отдельного клона
установленным приложением: doctor, проверка схемы/аккаунта, инициализация
существующей базы и сохранность записей OMEMO. Ни XMPP, ни модель не запускаются;
подключение к сети в проверяющем процессе запрещено. Исходная копия не мигрируется,
рабочий каталог данных не является целью восстановления.

После успешной проверки копия атомарно публикуется и только затем выполняется
ротация. Каталоги — 0700, файлы — 0600, владелец системных копий — root.
Копии содержат секреты и переписку; публиковать их или присылать в чат не нужно.

## Подключение к установленной 0.3.3

На VDS выполнять по одному шагу, проверяя вывод. Перезагрузка ОС не требуется.

1. Обновить выбранный проверенный коммит через существующую команду:

```bash
# До слияния в main заменить ПРОВЕРЕННЫЙ_SHA полным SHA этой версии.
sudo goose-update --ref ПРОВЕРЕННЫЙ_SHA
/opt/goose-xmpp-bot/venv/bin/goose-bot --version
```

Ожидаются версия 0.3.4, проверенная копия перед обновлением, готовое XMPP.
После слияния достаточно обычного `sudo goose-update`.
Рабочие настройки, ключи, режимы и образ сохраняются по правилам обновлятора.

2. Один раз включить регулярное копирование через команду установленного пакета:

```bash
sudo /opt/goose-xmpp-bot/venv/bin/goose-backup enable
```

Эта команда регистрирует короткий `goose-backup`, делает первую копию с пробным
восстановлением и лишь после успеха включает таймер. Службу Гуся не останавливает.
Первый запуск через полный путь работает и при переходе со старого обновлятора,
который ещё не умеет регистрировать новую короткую команду.

3. Посмотреть фактическое расписание и результат:

```bash
sudo goose-backup status
sudo systemctl list-timers goose-xmpp-bot-backup.timer --no-pager
sudo systemctl is-active goose-xmpp-bot.service
```

Ожидаются таймер active/enabled, ближайшие 04:15 по Москве, успешная первая
копия и отметка выполненного пробного восстановления; сам Гусь — active.
Время в `list-timers` отображается в часовом поясе сервера, выражение OnCalendar
явно содержит Europe/Moscow. `AccuracySec=1min` допускает запуск в пределах минуты.

4. Отдельно проверить именно службу, которую запускает таймер:

```bash
sudo systemctl start goose-xmpp-bot-backup.service
sudo journalctl -u goose-xmpp-bot-backup.service -n 30 --no-pager
sudo goose-backup status
```

Успешный ручной `create` не заменяет эту проверку изолированного systemd-сервиса.
После неё проверить новый ответ Гуся в прежнем auto. Следующим утром посмотреть
время нового автоматического запуска — это отдельное подтверждение календаря.
До фактического выполнения этих шагов живая приёмка таймера не заявляется.

## Команды

| Команда | Действие |
| --- | --- |
| `sudo goose-backup create` | Новая проверенная копия сейчас, с ротацией |
| `sudo goose-backup list` | Регулярные копии и проверка их целостности |
| `sudo goose-backup status` | Расписание, состояние таймера, последний системный запуск и результат последней попытки |
| `sudo goose-backup verify /путь/к/копии` | Хеши, права и целостность SQLite |
| `sudo goose-backup restore-test /путь/к/копии` | Изолированное восстановление и проверка приложением |
| `sudo goose-backup configure --keep 7` | Меняет число сохраняемых регулярных копий |
| `sudo goose-backup configure --calendar '*-*-* 03:30:00 Europe/Moscow'` | Меняет расписание |
| `sudo goose-backup disable` | Выключает только будущие запуски таймера |
| `sudo goose-backup enable` | Проверяет новую копию и включает таймер |

`configure` не включает выключенный таймер. Новое число копий применяется
при следующем успешном `create`. Допустимо от 2 до 365 копий, по умолчанию 14.
Расписание проверяется `systemd-analyze calendar` до изменения файлов.
При ошибке применения таймера возвращаются прежние настройки его unit.
Изменения затрагивают только службу/таймер копирования.

Пути нестандартной установки задаются до подкоманды: например,
`/путь/venv/bin/goose-backup --prefix /srv/goose enable`.
После регистрации короткая команда запоминает этот prefix. Системная установка
предполагает один набор unit Гуся, как и прежний установщик.

## Размещение и ротация

- Регулярные копии: `/var/backups/goose-xmpp-bot/scheduled/daily-*`.
- Настройки: `/opt/goose-xmpp-bot/backup-settings.json`, root:root 0600.
- Сводка последней попытки: `scheduled/status.json`.
- Unit: `goose-xmpp-bot-backup.service` и `goose-xmpp-bot-backup.timer`.
- Имена копий и manifest используют UTC; расписание — указанный часовой пояс.

Хранятся последние 14 **успешных копий**, а не обязательно 14 разных дней:
ручные `create` и первая копия при `enable` тоже входят в это число.
Ротация выбирает только собственные проверенные регулярные копии этой установки.
Повреждённые, чужие и неизвестные каталоги сохраняются для ручного разбора.
Каталоги `update-*`, созданные прежним обновлятором, не удаляются.

При недостатке места старая копия не удаляется ради попытки сделать новую.
Поэтому нужно учитывать место для новой копии и пробного восстановления,
а также отдельно сохраняемых копий перед обновлениями. Недостающий запас
выявляется до копирования. Незавершённые каталоги после жёсткого прерывания
не считаются пригодными копиями и показываются в status для ручной проверки.

Общая блокировка не позволяет резервированию и `goose-update` менять состояние
одновременно. Если обновление занято, копия завершается кодом 75; systemd
повторяет попытку через 10 минут, максимум три старта за час. Ошибка настроек
с кодом 2 не зацикливается. На работу других служб это не влияет.

Таймер Persistent наверстывает пропущенный календарный запуск после включения
или загрузки ОС. Сервис ограничен пятью минутами, SQLite-копирование — двумя;
у него понижен приоритет CPU/I/O, закрыта сеть, доступ на запись оставлен
каталогу копий и общей блокировке. Файл окружения Гуся не загружается как код.

Обновления сохраняют настройки, включённый таймер и стабильный путь команды.
Они могут обновить код служебной команды, но не заменяют пользовательское
расписание и не выключают настроенный таймер.

## Проверка восстановления и настоящий возврат данных

`restore-test` принимает и регулярные копии, и прежние `update-*` с manifest
поддерживаемого формата. Он проверяет копию, переносит её в отдельный временный
каталог, открывает установленным приложением и удаляет только пробный каталог.
Проверка не отправляет сообщений, не публикует ключей и не включает auto.

Пробная миграция может менять **только клон**. Если текущий код не принимает
схему или конфигурацию копии, проверка завершается ошибкой; исходная копия и
рабочая SQLite сохраняются. Это проверка пригодности к восстановлению, а не
запуск второго рабочего устройства OMEMO.

Автоматической команды, подменяющей рабочую SQLite, в этом этапе нет.
Для настоящего восстановления после аварии владелец отдельно выбирает копию
и совместимую версию кода. Порядок разбора:

1. Проверить копию и её пробное восстановление. Остановить все экземпляры,
   использующие **эту идентичность устройства бота**.
2. Сохранить действующий каталог данных целиком, включая WAL/SHM, если он
   ещё доступен. Выбрать, какие данные действительно потеряны: иногда нужно
   вернуть профили/историю, сохранив более свежие ключи.
3. При необходимости полного возврата восстановить согласованный набор
   SQLite/конфига/env/образа в ожидаемые пути. Каталог данных — владелец
   goose-xmpp-bot, 0700; SQLite — тот же владелец, 0600. Конфиг/env/образ —
   root:goose-xmpp-bot, 0640. Не смешивать старую SQLite с оставшимися новыми WAL/SHM.
4. До подключения проверить локальный doctor, аккаунт и совместимость OMEMO.
   Только после отдельного выбора владельца возобновлять XMPP.

Старая копия содержит более старые ratchet/prekey и не является безопасным
безусловным откатом работающей идентичности. Возможны потери сообщений после
момента копии. Поэтому копирование и пробный restore никогда не возвращают
рабочие ключи назад. Этот порядок не был выполнен на семейном VDS и не выдаётся
за проверенное аварийное восстановление боевой идентичности.

## Ограничения

Локальные копии остаются на том же VDS; перенос на независимый носитель,
шифрование внешнего архива и уведомления об отказе — отдельные задачи.
Неизвестный файл в каталоге данных блокирует копирование: текущая версия знает
SQLite и её служебные файлы, а не обещает согласованно скопировать произвольное
новое хранилище. Изменение конфига во время копии также отменяет попытку.
Предыдущие проверенные копии при этом сохраняются.

Обычные тесты не используют настоящие XMPP/API/секреты. Результаты и границы
проверок, включая установленный wheel и подставной systemd, находятся в
[отчёте](BACKUPS_REPORT.md). Загрузка VDS не проверяется без отдельной команды.
