# Базовая установка и XMPP

Для версии 0.2.0 сначала прочитайте [переход на этап 2](INSTALLATION_STAGE2.md):
перед запуском новой версии нужна копия данных из-за миграции схемы SQLite.

Целевая система — Ubuntu 24.04 x86_64 с Python 3.12. Нужны исходящие DNS и XMPP-подключения к домену **отдельного тестового аккаунта**, TLS с доверенным сертификатом, доступ к PyPI для установки. Реальный домен задаётся владельцем; `example.org` в примерах вымышлен. Основной аккаунт, действующий Prosody и другие службы не меняются.

## Подготовка версии

```bash
sudo apt-get update
sudo apt-get install python3.12-venv git ca-certificates
git clone https://github.com/ivancher-dev/goose-xmpp-bot.git
cd goose-xmpp-bot
# Замените COMMIT_SHA полным SHA проверенного коммита PR или выпуска.
git checkout --detach COMMIT_SHA
git status --short
sudo bash scripts/install.sh
```

Установщик требует чистый checkout с существующим HEAD, не выполняет `git pull`, не меняет Prosody/nginx/firewall и не запускает службу без `--start`. Он создаёт системного пользователя `goose-xmpp-bot` без входа, virtualenv, конфигурацию и файл окружения только при их отсутствии, unit systemd. Установка зависимостей использует `requirements.lock`, хеши и обычную проверку TLS. Рабочие данные находятся вне исходников.

Параметры: `--prefix /opt/goose-xmpp-bot`, `--config /etc/goose-xmpp-bot/config.toml`, `--data-dir /var/lib/goose-xmpp-bot`, `--env-file /etc/goose-xmpp-bot/goose.env`. Пути абсолютные, без пробелов/специальных символов. Код, данные и исходный checkout не должны перекрываться. Systemd-установка отклоняет пути внутри `/tmp`, `/var/tmp`, `/home`, `/root`, `/run/user`, скрытые настройками изоляции unit. Если существующий конфиг содержит другой `data_dir`, установка завершается ошибкой и сохраняет конфиг.

При повторном выполнении настройки, пароль, профили и ключи не перезаписываются. Существующий каталог данных должен иметь права `0700`. Код и venv принадлежат root, данные — сервисному пользователю, конфиг и файл окружения — `root:goose-xmpp-bot` с правами `0640`. Родительские каталоги настроек должны разрешать сервисному пользователю проход; установщик проверяет локальную диагностику от его имени.

Checkout может находиться в `/root`: после установки диагностика запускается из доступного каталога `prefix`, а не из каталога исходников. Для установленной до этого исправления версии сообщение «Ошибка выполнения; проверьте права, зависимости, SQLite и доступность XMPP» сразу после установки пакета может быть вызвано унаследованным недоступным каталогом. Повторите только локальную проверку из каталога установки:

```bash
cd /opt/goose-xmpp-bot
sudo -u goose-xmpp-bot ./venv/bin/goose-bot doctor \
  --config /etc/goose-xmpp-bot/config.toml
```

Эта команда не подключается к XMPP и не создаёт OMEMO-устройство. После обновления до исправленного коммита можно повторить установку; существующие конфигурация и данные сохраняются.

Начиная с 0.3.3 повторные установки выполняет `sudo goose-update`:
он готовит окружение до остановки, делает проверенную копию и переключает код.
Для существующей 0.3.2 сначала однократно подключить команду через
[setup-updater.sh](SAFE_UPDATES.md). `install.sh` поверх обслуживаемого
обновлятором venv отклоняется. Регулярные копии остаются следующей задачей.

## Настройки владельца

Отредактируйте `/etc/goose-xmpp-bot/config.toml`: тестовый JID, отдельный resource, JID управляющего аккаунта, allowlist, начальные профили и часовой пояс. Номер класса и идентификатор группы расписания меняются независимо. Начните с выключенной модели, `schedule.enabled=false` и `manual`; TLS/OMEMO обязательны. Модель включается по [INSTALLATION_STAGE2.md](INSTALLATION_STAGE2.md). `echo_enabled=true` включается только для теста владельца.

В `/etc/goose-xmpp-bot/goose.env` безопасным редактором задайте `GOOSE_XMPP_PASSWORD` согласно синтаксису systemd `EnvironmentFile`. Значение не передаётся аргументом процесса и не помещается в Git/чат/журналы. Если изменили `password_env`, используйте такое же имя в файле. Пока модель выключена, ключ её API не нужен.

```bash
sudo -u goose-xmpp-bot /opt/goose-xmpp-bot/venv/bin/goose-bot doctor \
  --config /etc/goose-xmpp-bot/config.toml
sudo systemctl enable --now goose-xmpp-bot.service
sudo systemctl is-active goose-xmpp-bot.service
sudo journalctl -u goose-xmpp-bot.service -n 30 --no-pager
```

Локальный `doctor` не авторизуется в XMPP и не читает `goose.env`. При `sudo -u` он обычно не видит пароль, который systemd передаёт только сервису. Строка «Пароль XMPP: не передан текущему процессу» и отсутствие SQLite до первого запуска — информационные сообщения, а не ошибки. Успешная локальная проверка завершается с кодом 0; пароль требуется для `run` и `doctor --xmpp`. После запуска журнал должен содержать `xmpp_ready` с результатом discovery. Состояние `active` само по себе не подтверждает работоспособность: выполните зашифрованный `!ping` по [TESTING_XMPP.md](TESTING_XMPP.md).

На один процесс допускаются до трёх сессий (настройка `max_attempts`) с задержкой 1/2 секунды перед повторами и таймаутом инициализации 45 секунд. Ошибки авторизации и инициализации OMEMO завершают процесс без повторов. После исчерпания попыток нужен осознанный `systemctl restart`; бесконечного цикла перезапуска systemd нет. SIGTERM закрывает XMPP и задачи, сохраняя БД.

## Диагностика XMPP без изменения OMEMO

Только явный `--xmpp` подключается к тестовому аккаунту. У него случайный отдельный resource `doctor-*`; OMEMO-плагин не загружается, новая идентичность не создаётся, решения доверия не меняются. Диагностика проверяет авторизацию, TLS, roster и discovery Carbons/MAM, затем закрывает соединение. Это не проверка шифрования с клиентами.

Carbons запрашиваются у домена, поддержка MAM 2 — отдельным сетевым `disco#info` у bare JID аккаунта. `MAM=True` означает объявленную поддержку, `False` — отсутствие `urn:xmpp:mam:2` в корректном ответе аккаунта. При IQ-ошибке или таймауте остаётся «не проверено», в журнал выводится `xmpp_discovery_incomplete feature=mam`; эта необязательная проверка не препятствует запуску чата. Таймаут запроса — 10 секунд. Содержимое архива эта диагностика не запрашивает.

```bash
sudo systemd-run --pipe --wait --collect --uid=goose-xmpp-bot \
  --property=EnvironmentFile=/etc/goose-xmpp-bot/goose.env \
  /opt/goose-xmpp-bot/venv/bin/goose-bot doctor \
  --config /etc/goose-xmpp-bot/config.toml --xmpp
```

Для локальной диагностики и состояния systemd есть `scripts/doctor.sh --config ...`; другой Python задаётся `GOOSE_PYTHON=/путь/к/python`. Ошибки основной команды сохраняют ненулевой статус; просмотр systemd не заменяет их.

## Устройства и ручное доверие

Доверие новым устройствам автоматически не выдаётся. Сначала запустите сервис один раз для создания и публикации идентичности, затем остановите его. Все команды `devices`/`trust` работают с тем же каталогом и блокировкой; одновременный доступ второго экземпляра запрещён. Это явные сетевые команды управления, в отличие от `doctor`.

```bash
sudo systemctl stop goose-xmpp-bot.service
# Собственное устройство бота и другие устройства тестового аккаунта:
sudo systemd-run --pipe --wait --collect --uid=goose-xmpp-bot \
  --property=EnvironmentFile=/etc/goose-xmpp-bot/goose.env \
  /opt/goose-xmpp-bot/venv/bin/goose-bot devices \
  --config /etc/goose-xmpp-bot/config.toml
# Повторите команду devices с --jid parent@example.org для управляющего аккаунта.
# Для каждого нужного устройства сверяйте отпечаток в самом клиенте по независимому каналу.
sudo systemd-run --pipe --wait --collect --uid=goose-xmpp-bot \
  --property=EnvironmentFile=/etc/goose-xmpp-bot/goose.env \
  /opt/goose-xmpp-bot/venv/bin/goose-bot trust \
  --config /etc/goose-xmpp-bot/config.toml \
  --jid parent@example.org --device-id DEVICE_ID --fingerprint VERIFIED_FINGERPRINT
sudo systemctl start goose-xmpp-bot.service
```

В командах выше JID, `DEVICE_ID` и `VERIFIED_FINGERPRINT` заменяются фактическими значениями тестового аккаунта и проверенного устройства. Отпечаток — 64 шестнадцатеричных символа Curve25519, как в выводе `devices`; пробелы допустимы внутри кавычек. Несовпадение отпечатка не меняет доверия. Для отзыва используется та же команда с `--distrust`. Доверие хранится для ключа, поэтому замена идентичности требует новой проверки.

Проверьте также устройства самого тестового аккаунта: библиотека шифрует копии и для них. При непроверенном доступном устройстве или возвращённых ошибках шифрования ответ блокируется целиком. Библиотека может пропускать устройства с недоступным bundle при построении списка; сверяйте список `devices` со списком в клиенте. Новые или устаревшие устройства разбираются владельцем; не включайте слепое доверие как исправление.

У собственного текущего устройства бота в выводе `devices` допустим `UNDECIDED`: менеджер OMEMO исключает его из получателей при шифровании. Ручная проверка доверия требуется для остальных устройств аккаунта и собеседника. Собственное устройство определяйте по ID и отпечатку, сверенным при первоначальной настройке.

В Gajim и Conversations владелец отдельно сверяет и подтверждает устройство бота. Перезапуск сервиса должен сохранить его ID/отпечаток. Поддерживается только legacy OMEMO; клиент с OMEMO 2 без legacy несовместим с этой версией. Неподдерживаемый или открытый вход не получает открытого ответа.

Подтверждение отпечатка в Gajim не включает шифрование чата автоматически: в меню шифрования рядом с полем ввода выберите OMEMO, затем отправьте новую диагностическую команду. Доверие в Gajim и в хранилище бота задаётся отдельно; зелёный статус в клиенте не заменяет команду `goose-bot trust` для нужного проверенного устройства.

## Данные и ограничения

`goose.sqlite3` содержит профили, OMEMO-ключи, сессии, доверие и хеши дедупликации; схема 2 добавляет режимы и ограниченную память при включённой модели. БД привязана к bare JID аккаунта и не может использоваться для другого аккаунта. Остановив все процессы Гуся, сделайте защищённую резервную копию всего каталога данных, конфига, файла окружения и образа Гуся. Не удаляйте БД ради «починки» соединения: это уничтожает идентичность и доверие. Неизвестная версия схемы отклоняется; автоматического отката схемы нет.

Сервис объявляет presence с приоритетом `0`, позволяющим серверу доставлять сообщения на bare JID. Временные `doctor --xmpp`, `devices` и `trust` используют `-1` и не обрабатывают команды. При подключении других клиентов одного приоритета недостаточно для гарантии доставки: требуется [живая проверка маршрутизации](TESTING_XMPP.md).

Живая входящая Carbon-копия (`received`) принимается только от точного bare JID самого бота, с единственным forwarded-сообщением, адресованным тому же аккаунту. По внутреннему отправителю проверяется allowlist, затем выполняются обычные дедупликация, расшифровка и проверка доверия устройству. Прямая доставка и Carbon одной команды не создают два ответа. Поддельные/вложенные оболочки, исходящие `sent`, MAM, остальные forwarded, delayed, служебные события, собственные сообщения и квитанции команды не выполняют. На этапе 1 архив не восстанавливается в историю и автоматический ручной перехват не реализован.

В журнале `message_received source=direct` или `source=received-carbon` означает допуск в очередь, а `reply_queued` — передачу зашифрованного ответа в очередь отправки, без подтверждения доставки клиенту. `reply_blocked reason=manual_trust_required` требует проверки устройств собеседника и самого тестового аккаунта; доверие без сверки не выдаётся.

Дедупликация хранит SHA-256 от bare JID и origin-id либо stanza id до 7 суток, максимум 10 000 записей. Без ID используется хеш XML на 60 секунд; изменение XML может обойти такую эвристику. Повторная доставка отмечается **до** исполнения команды, поэтому после сбоя БД/шифрования для повторной команды нужен новый ID. Это ограниченная защита, а не гарантия exactly-once.

Одна очередь на 64 сообщения обрабатывается последовательно; размер XML ограничен 64 КиБ, расшифрованного текста — 2048 символами, обработка одного сообщения — 30 секундами. Переполнение отбрасывается без ответа. Журналы содержат только фиксированные коды причин и технические флаги; библиотечное логирование XML/JID отключено. Ограничения памяти XMPP-парсера до admission не доказаны; ресурсные лимиты systemd выбираются после пилотных измерений.

## Изолированная проверка установщика без root

```bash
# Checkout должен быть чистым; команды не запускают XMPP/systemd.
test_root=$(mktemp -d /tmp/goose-install.XXXXXX)
bash scripts/install.sh --local --prefix "$test_root/app" \
  --config "$test_root/etc/config.toml" --data-dir "$test_root/data" \
  --env-file "$test_root/etc/goose.env"
# Повторите ту же команду и убедитесь, что конфигурация и БД сохранены.
```

`--local` не создаёт системного пользователя и не регистрирует/запускает службу; он выполняет настоящую установку зависимостей и пакета и рендерит unit в prefix. Настоящая systemd-установка и клиентская приёмка отдельно проверяются на тестовой VDS.
