# Обновление Гуся одной командой, 0.3.3

[Задание](tasks/05a-safe-updates.md). Этот эксплуатационный этап вынесен перед
расписанием по просьбе владельца. Схема SQLite остаётся 4, зависимости прежние.
Регулярные копии по таймеру — отдельная следующая задача; здесь обязательна
проверенная копия перед каждой активацией версии.

## Как пользоваться

После однократного подключения:

```bash
sudo goose-update
```

Команда загружает `main` из `origin`, фиксирует конкретный SHA, собирает
отдельное окружение с зависимостями из lock-файла и проверяет его до остановки
действующего Гуся. Затем останавливает только `goose-xmpp-bot.service`, делает
защищённую копию, проверяет миграцию на отдельном клоне, переключает окружение
и ждёт готовности XMPP нового процесса. После успеха включает автозапуск.
Prosody, nginx, firewall и остальные службы не меняются.

Другие варианты:

```bash
# Только скачать, собрать и проверить. Без остановки, миграции и смены активной версии.
sudo goose-update --check
# Выбранная ветка, тег или полный SHA, доступный в origin.
sudo goose-update --ref feat/safe-one-command-updates
# При медленном подключении: ожидать новый XMPP до 5 минут вместо обычных 4.
sudo goose-update --timeout 300
# После прерванной операции — отдельная попытка безопасного возврата прежнего кода.
sudo goose-update --recover
```

Обновлятор устанавливает только версии с протоколом готовности 0.3.3 и новее.
Переход на старые 0.3.2 через `--ref` не поддерживается; автоматический возврат
предыдущего окружения при неудаче первой установки поддерживается.
Команда с `--check` тоже использует сеть Git/pip, но не XMPP и не API модели.

## Однократное подключение к установленной 0.3.2

Все команды выполняются на том же VDS, где работает Гусь. В сопровождении
через чат выполнять по одному шагу, проверяя результат. Перезагрузка VDS не нужна.

1. В чистом `/root/goose-xmpp-bot` загрузить ветку, проверить SHA и выбрать
   именно проверенный коммит. Не использовать `reset --hard` или удаление правок:

```bash
cd /root/goose-xmpp-bot
git status --short --branch
git fetch origin feat/safe-one-command-updates
git log -1 --oneline FETCH_HEAD
# После проверки заменить ЗАФИКСИРОВАННЫЙ_SHA полным хешем из выбранной версии:
git switch --detach ЗАФИКСИРОВАННЫЙ_SHA
```

2. Зарегистрировать обновлятор. Он использует системный Python 3.12 со
   стандартной библиотекой. Старые venv, unit, данные и работающий процесс
   на этом шаге не меняются; создаются только настройки и команда обслуживания:

```bash
sudo bash scripts/setup-updater.sh
```

3. Выполнить первую установку через новый механизм. До слияния в main указать
   тот же проверенный SHA ветки, после слияния достаточно `sudo goose-update`:

```bash
sudo goose-update --ref ЗАФИКСИРОВАННЫЙ_SHA
```

Ожидаются сообщения о проверенной копии, готовом XMPP и включённом автозапуске.
Проверка режимов выводится только суммарно, без JID и текстов переписки.
Если нужно сначала проверить загрузку и сборку, добавить `--check`, затем
повторить без него. При обычных последующих обновлениях checkout переключается
на установленный SHA; запускать `git switch` и `install.sh` больше не требуется.

4. Проверить службу и версию:

```bash
/opt/goose-xmpp-bot/venv/bin/goose-bot --version
sudo systemctl is-active goose-xmpp-bot.service
sudo systemctl is-enabled goose-xmpp-bot.service
sudo journalctl -u goose-xmpp-bot.service --since "2 minutes ago" -n 30 --no-pager
```

Ожидаются `0.3.3`, `active`, `enabled`, `xmpp_ready` и успешная проверка архива.
После этого отправить **новый** обычный вопрос в ранее включённый auto-диалог:
ожидается один ответ. Посмотреть режим заранее оставленного manual-диалога:
он должен остаться manual. Не присылать содержимое env, БД или копий в чат.

Свежий `install.sh` для новой установки также регистрирует обновлятор.
Прямую повторную установку поверх обслуживаемого venv он отклоняет, чтобы
обновление не обошло копирование и журнал. По умолчанию `install.sh` по-прежнему
только готовит файлы; первый запуск новой конфигурации остаётся явным.

Для нестандартных путей `setup-updater.sh` принимает те же `--prefix`, `--config`,
`--data-dir`, `--env-file`, что и установщик. Пути сохраняются в root-only
`/opt/goose-xmpp-bot/maintenance.json`. Их нельзя размещать внутри checkout,
venv, каталога данных или копий. `llm.persona_file` учитывается отдельно,
в том числе когда он лежит вне каталога конфига.

## Режимы и восстановление соединения

Новый диалог начинается в manual. Прежний подтверждённый auto возвращается
после полной проверки MAM от сохранённой позиции и при включённых Carbons.
Ручная реплика с другого устройства по-прежнему включает manual только
соответствующего собеседника и отменяет ожидающий ответ.

Временный таймаут MAM сохраняет подтверждённую позицию и ставит auto на паузу.
Следующая успешная проверка, обычно через минуту, снимает такую паузу.
Неудавшийся discovery MAM также повторяется. Удалённая позиция, некорректный
архив, неподдерживаемые Carbons/MAM или первый запуск не дают безусловного auto:
нужны диагностика и, при необходимости, явное подтверждение владельца.
Просмотр `!admin mode <bare_jid>` различает временную паузу и потерю позиции.
Старые вопросы из архива не выполняются заново.

systemd использует `Type=notify`: active означает готовое XMPP-соединение
после начальной проверки архива. Неполный архив может оставлять отдельные
диалоги на паузе при уже активном соединении. После исчерпания ограниченных
сетевых попыток процесс выходит с кодом 75, systemd запускает его снова
через 30 секунд. Временные IQ/сетевые ошибки при инициализации OMEMO тоже
требуют нового процесса, а не повторного использования частично созданного
менеджера. Ошибки конфигурации, ключей и авторизации имеют код 2 и не зацикливаются.
Обычный `systemctl stop` не вызывает самопроизвольного запуска. При загрузке ОС
службу запускает systemd, если она enabled; обновлятор его включает после успеха.

## Копии и неудачные обновления

Копии находятся в `/var/backups/goose-xmpp-bot/update-*`, каталог — 0700,
файлы — 0600. Под остановленным сервисом и блокировкой хранилища копируются
данные, конфиг, env, реальный файл образа и unit. Проверяются контрольные суммы,
SQLite и миграция отдельного клона; сама сохранённая копия не мигрируется.
Проверка модели и отправка тестовых вопросов не выполняются.

Копии содержат секреты и историю. В этом этапе они **не удаляются автоматически**:
следить за диском и хранить их только в защищённом месте. Перед остановкой
обновлятор проверяет запас места для резервной и пробной копий; это не заменяет
наблюдение за диском. Регулярная ротация и внешнее хранение будут отдельной задачей.

Активный путь остаётся `/opt/goose-xmpp-bot/venv`. Подготовленные окружения
находятся в `releases/`, переключение ссылки атомарное. Сохраняются текущая и
предыдущая версии; удаляются только собственные отмеченные каталоги.
Первое прежнее окружение сохраняется отдельно в `legacy-*` и не удаляется
автоматически. Настройки, внешний образ и каталог данных обновлятор не заменяет.

При неудачной активации обновлятор останавливает новую версию и может вернуть
старый код/unit, если схема SQLite прежняя, версии runtime-зависимостей совпадают
и старый doctor принимает действующие данные. Если служба до операции была
выключена, ошибка её не включает. Успешная операция запускает и включает службу.

**Рабочая OMEMO-база не восстанавливается автоматически из копии.** Она могла
продвинуть состояние шифрования и получить сообщения после копирования.
Несовместимые схема/зависимости оставляют службу остановленной, новые данные
сохранёнными и журнал операции доступным для отдельного разбора.

Прерывание обнаруживается по `update-state.json`. Следующий запуск не начинает
ещё одну установку поверх него; `--recover` пытается вернуть прежний код по
тем же проверкам. Если откат запрещён, не удалять журнал и не подкладывать старую
БД: сначала разбирать совместимость на отдельной копии. Возврат кода после
прерывания может остановить уже успевшую запуститься новую версию.

Вывод подпроцессов Git/pip скрыт, чтобы не раскрывать URL с ключами или тело
ошибок. При отказе выводятся этап и код команды. Ошибка загрузки или сборки
до активации не останавливает действующего Гуся. Параллельные обновления,
грязный checkout, смена настроек во время сборки и занятая БД блокируют переключение.

## Приёмка

Автоматические проверки используют временные базы, подставной systemd и
UNIX-сокет готовности. Настоящий installed-wheel переход отдельно проверяется
с `--local`: он не запускает systemd, XMPP и модель. Итог и точные результаты:
[отчёт](SAFE_UPDATES_REPORT.md).

На VDS после установки остаётся проверить по одному сценарию:

1. Первая установка через обновлятор: active/enabled, прежний auto отвечает,
   manual сохраняется, образ и города прежние, нет повторов архивных команд.
2. Ещё одно обновление выбранного SHA одной командой и новый вопрос из обоих
   клиентов. Сам обновлятор платный вопрос не отправляет.
3. Перезапуск **только службы** с восстановлением auto после MAM.
4. При разрешении владельца — временный сетевой сбой только тестового бота.
   Не менять общий firewall или другие службы ради этой проверки.

Перезагрузка VDS отложена владельцем; запуск при загрузке проверяется
по unit/enable и офлайн-модели отказов. Живая проверка загрузки ОС не заявляется.

Протокол готовности: [sd_notify](https://www.freedesktop.org/software/systemd/man/latest/sd_notify.html),
политики запуска: [systemd.service](https://www.freedesktop.org/software/systemd/man/latest/systemd.service.html).
