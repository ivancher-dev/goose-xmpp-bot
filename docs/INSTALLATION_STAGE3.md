# Обновление на 0.3.0: ручная переписка и MAM

Переход с установленной 0.2.5 на том же VDS, Ubuntu 24.04/Python 3.12.
Меняется только сервис Гуся. Перезагрузка VDS и изменения Prosody/nginx/firewall
не нужны. Существующие TOML, env, образ, профили, города, память и ключи сохраняются.
Новых параметров конфигурации и ключей API нет.

Схема SQLite становится **4** при первом `run`/управлении устройствами.
Локальный doctor не мигрирует базу. Старые версии схему 4 отвергают.
Перед первым запуском нужна свежая копия, взятая после остановки бота.

## 1. Выбрать фиксированный коммит

В checkout на сервере, в одной SSH-сессии с последующими шагами:

```bash
cd /root/goose-xmpp-bot
git status --short --branch
git fetch origin feat/stage3-owner-takeover
git log -1 --oneline FETCH_HEAD
goose_stage3_commit=$(git rev-parse FETCH_HEAD)
```

Сверьте SHA с выбранной версией. При несохранённых изменениях сначала сохраните
их; установщик работает только из чистого checkout. Detached HEAD допустим.

## 2. Остановить бот, скопировать и проверить данные

```bash
sudo systemctl stop goose-xmpp-bot.service
sudo install -d -m 0700 /var/backups/goose-xmpp-bot
goose_stage3_backup=$(sudo mktemp -d /var/backups/goose-xmpp-bot/stage3.XXXXXX)
sudo cp -a /var/lib/goose-xmpp-bot "$goose_stage3_backup/data"
sudo cp -a /etc/goose-xmpp-bot "$goose_stage3_backup/config"
git rev-parse HEAD | sudo tee "$goose_stage3_backup/code-commit.txt" >/dev/null
sudo python3 - "$goose_stage3_backup" <<'PY'
from pathlib import Path
import sqlite3, sys
root = Path(sys.argv[1])
with sqlite3.connect((root / 'data/goose.sqlite3').as_uri() + '?mode=ro', uri=True) as db:
    assert db.execute('PRAGMA quick_check').fetchone()[0] == 'ok'
    print('Схема копии:', db.execute('PRAGMA user_version').fetchone()[0])
for name in ('config.toml', 'goose.env', 'persona.md'):
    assert (root / 'config' / name).is_file(), name
print('Копия проверена:', root)
PY
```

При любой ошибке копирования/проверки установку не продолжайте. Сохраните путь
копии. Если образ хранится по другому пути, скопируйте его отдельно. Старые
копии предыдущих обновлений не заменяют эту: в них могут быть устаревшие
OMEMO-сессии. Копию, env и базу не публикуют и не добавляют в Git.

## 3. Установить выбранный код

```bash
git switch --detach "$goose_stage3_commit"
sudo bash scripts/install.sh
/opt/goose-xmpp-bot/venv/bin/goose-bot --version
```

Ожидается `0.3.0` и успешная локальная диагностика. Пока сервис не запущен,
doctor может показывать прежнюю схему 3. Сообщение о непереданных текущему
процессу секретах не означает потерю env: служба читает свой EnvironmentFile.

## 4. Запустить и проверить

```bash
sudo systemctl start goose-xmpp-bot.service
sudo systemctl status goose-xmpp-bot.service --no-pager --full
sudo journalctl -u goose-xmpp-bot.service -n 40 --no-pager
sudo -u goose-xmpp-bot /opt/goose-xmpp-bot/venv/bin/goose-bot doctor \
  --config /etc/goose-xmpp-bot/config.toml
```

После завершения подключения ожидаются `active`, схема 4, `xmpp_ready` и
`archive_sync_finished`. Первая синхронизация ставит исходные позиции архива
без импорта старых сообщений. Это сохраняет прежнюю очистку контекста и не
обещает расшифровать архив до добавления устройства бота.

Со своего управляющего аккаунта отправьте отдельными сообщениями для тех
диалогов, где действительно нужен auto; подставьте свои разрешённые bare JID:

```text
!admin mode parent@example.org auto
```

```text
!admin mode pupil1@example.org auto
```

Профиль для auto должен существовать, как в 0.2.5. Первый явный auto подтверждает
новую исходную позицию. Подтверждение нужно отдельно для каждого диалога.

## 5. Живая приёмка, по одному сценарию

Этап 3 ещё не объявляется принятым по одним офлайн-тестам. Сначала проверьте
с владельцем, затем другим разрешённым аккаунтом. Записывайте результат без
реальных JID, ключей и переписки. Для Gajim и Conversations повторите отдельно.

1. Новый вопрос от собеседника получает один зашифрованный ответ модели.
2. Из обычного клиента **под аккаунтом Гуся**, с другим resource, напишите
   этому собеседнику вручную. Со своего управляющего аккаунта запросите
   `!admin mode <его bare_jid>`: ожидается manual. Новый свободный вопрос
   не вызывает автоответ; другой диалог продолжает работать. Погода/новости
   по явному запросу доступны и в manual.
3. Включите auto явно. Уточнение должно учитывать ручной ответ в памяти.
   Текст импортируется только при успешной расшифровке доверенного устройства
   Гуся. Если в журнале `manual_message_seen text_restored=False`, проверьте
   OMEMO/доверие; открытая или нерасшифрованная отправка только включает паузу.
4. Во время долгого ответа модели включите явный manual. Неотправленный ответ
   не должен прийти позже; проверьте также ручную отправку во время ожидания.
5. Снова включите auto, перезапустите **только сервис Гуся**. При успешном MAM
   и Carbons новый вопрос получает ответ без повторного auto. Сам перезапуск
   не создаёт ответа на прежний вопрос.
6. Остановите только сервис, оставив обычный клиент Гуся подключённым. Напишите
   из него собеседнику вручную, затем запустите сервис. Архив должен вернуть
   этот диалог в manual, восстановить ручной текст и не запустить старые команды.
7. Очистите свой контекст, дождитесь очередной синхронизации (до минуты).
   Прежняя память не должна вернуться; профиль и город сохранены. Проверьте
   независимость второго диалога.
8. Проверьте повтор direct/received-carbon/sent-carbon: один вопрос даёт один
   ответ, собственные ответы сервиса не включают manual и не создают цикл.
   Отдельно проверьте bare/full JID и восстановление после обрыва сети только
   тестового сервиса, без воздействия на другие службы VDS.

## Условия и ограничения

- Живая отправка другого устройства определяется по проверенной прямой доставке
  или sent-carbon от точного bare JID Гуся. Нужны разные resource и доверие
  собственным OMEMO-устройствам, если требуется импорт ручного текста.
- Автопауза имеет сетевую задержку. Уже поставленный в XMPP-очередь ответ не
  отзывается. Для гарантированного вмешательства сначала отправьте явный manual
  и дождитесь подтверждения.
- MAM запрашивается только у своего аккаунта с фильтром по разрешённому
  собеседнику. Размер страницы — 50, до 5 страниц за диалог, до 64 КиБ на
  сообщение и 2 МиБ на страницу. IQ — до 5 секунд, общий бюджет синхронизации —
  20 секунд, до 10 секунд на собеседника с разделением оставшегося времени.
  Повторная фоновая проверка — раз в 60 секунд.
- Сохраняется RSM-позиция, а не предположение о часовом поясе сервера.
  Утрата позиции (`item-not-found`), нестабильная/неполная выдача, лимит или
  ошибка расшифровки запрещают автоматический auto этого диалога. Другой
  диалог восстанавливается независимо. Нужна явная команда владельца.
- Полнота зависит от хранения MAM на Prosody. Удалённые, не архивируемые и
  не зашифрованные для устройства бота сообщения восстановить нельзя.
  При проблеме создаётся новая исходная позиция, которая без явного auto
  не даёт разрешения отвечать. Позднее подтверждение означает продолжение
  с доступным контекстом, а не восстановление утраченных сообщений.
- Архивные вопросы сохраняются в пределах срока хранения и окна памяти,
  но сами не запускают ответы. Старые задания модели/инструментов не оживают.
- Хеши событий ограничены 10 000 записями/35 днями. При утрате всех устойчивых
  ID и изменённом ciphertext абсолютная дедупликация не обещается.

## Если запуск не удался

Остановите только бот, сохраните диагностические коды и текущие данные.
Ручная переписка обычными клиентами остаётся доступной. Не устанавливайте
0.2.5 поверх схемы 4 и не подменяйте рабочую OMEMO-базу старой копией без
отдельного плана: это может откатить криптографические сессии и потерять новые
сообщения. Автоматический откат/восстановление сервера относятся к этапу 5.
