# Живая приёмка этапа 1

Результаты заполняются по фактическим проверкам; непройденные сценарии остаются **не проверены**. Офлайн-тесты не подтверждают поведение Gajim/Conversations, Prosody, маршрутизацию или фактический TLS на VDS. Используйте отдельный тестовый аккаунт и вымышленные диагностические тексты, не действующий аккаунт Гуся и не переписку детей.

## Перед проверкой

1. Выполните [установку](INSTALLATION.md). Задайте тестовый JID, отдельный resource сервиса, отдельный управляющий аккаунт и два тестовых профиля в allowlist. Администратор — только управляющий аккаунт. Сохраните `manual`, отключённые LLM/schedule; сначала оставьте echo выключенным.
2. Зафиксируйте SHA (`git rev-parse HEAD`), Python (`python3.12 --version`), зависимости (`/opt/goose-xmpp-bot/venv/bin/python -m pip show slixmpp slixmpp-omemo oldmemo omemo`), Prosody (`prosodyctl about`, локально без публикации сведений сервера). Секреты не выводите.
3. В Gajim получите версию через «Справка → О программе» или `gajim --version`. В Conversations — «Настройки → О приложении». Запишите версию ОС, включённый OMEMO namespace и версию OMEMO-плагина Gajim, если он отдельный. Не делайте вывод о namespace по одному названию «OMEMO».
4. Выполните явный `doctor --xmpp` по инструкции установки. Сравните число устройств до и после: диагностическая команда не должна создавать новое устройство или менять доверие.
5. Запустите сервис, дождитесь `xmpp_ready`, остановите его и выполните `devices`/`trust` с проверкой отпечатков. В обоих клиентах отдельно подтвердите устройство бота. Проверьте также устройства других клиентов самого тестового аккаунта. Верните сервис в работу.

### Наблюдения владельца, 23 октября 2026 года

Первая успешная проверка выполнена на VDS с версией `03acc48`, Python 3.12, Slixmpp 1.17.0, slixmpp-omemo 2.2.0; владелец сообщил версию Prosody 13.0.4. Локальная диагностика проверила существующую SQLite схемы 1; явный `doctor --xmpp` завершился успешно. Владелец подтвердил получение `pong` после нового зашифрованного `!ping` сначала в Gajim 2.4.6 на Windows, затем в Conversations 2.20.4+free m149 на Android. Обработчик сервиса принимает только legacy OMEMO, поэтому успешный обмен подтверждает этот namespace для проверенного сценария с обоими клиентами.

До успешного обмена в меню чата Gajim было выбрано «Отключено», хотя отпечаток бота уже был подтверждён. После включения OMEMO ответ блокировался с `manual_trust_required`: требовалось отдельно сохранить доверие в хранилище бота к другим устройствам самого тестового аккаунта. После настройки в журнале наблюдались `message_received source=direct`, `reply_queued`, игнорирование `sent-carbon`, квитанции и собственного сообщения. Получение ответа подтвердил владелец; одного `reply_queued` для этого недостаточно.

После явного `systemctl restart` владелец повторно подтвердил получение зашифрованных ответов в обоих клиентах. Позднее, в установленной `41f4fc2`, сервис остановлен на время команды `devices` и снова запущен. ID и полный отпечаток собственного устройства совпали с первоначальными; два других устройства тестового аккаунта сохранили `TRUSTED`. У собственного устройства остался `UNDECIDED`, что допустимо: менеджер исключает его из получателей при шифровании. Реальные ID и отпечатки в отчёт не включаются.

Затем по запросу владельца ответ на `!ping` изменён на `Га-Га-Га!`. После установки `ca63fa4` локальная диагностика повторно подтвердила целостность существующей SQLite, сервис был запущен, и владелец подтвердил получение нового зашифрованного ответа в обоих клиентах. Новый текст проверен и офлайн, и в живом обмене.

В Gajim и Conversations отдельно проверены `!help` и свободное тестовое сообщение с включённым OMEMO. В обоих клиентах получена справка о диагностическом режиме, свободное сообщение осталось без автоответа.

Управляющий аккаунт успешно выполнил `!admin status`: соединение активно, модель и расписание отключены. Для `!echo` владелец подтвердил отказ при `echo_enabled=false`, корректный тестовый ответ после явного включения, затем повторный отказ после возврата `false` и перезапуска. В ответах об эхо клиенты дополнительно не различались; негативная проверка неадминистратора при включённом эхо остаётся открытой. По завершении проверки эхо выключено.

В версии `ca63fa4` флаг `MAM=False` получен из discovery домена. После установки `41f4fc2` исправленная проверка bare JID аккаунта дала `MAM=True`; владелец прислал ответ `!admin status` с активным соединением, legacy OMEMO, `Carbons=True`, отключёнными моделью и расписанием. Подтверждена объявленная поддержка MAM 2 аккаунтом на Prosody 13.0.4; содержимое архива не запрашивалось.

В установленной `41f4fc2` управляющий аккаунт прочитал четыре поля настроенного профиля, временно изменил класс и получил подтверждение обновления. После `systemctl restart` повторное чтение показало новый класс, остальные три поля сохранились. Затем класс возвращён к исходному значению и повторно прочитан; восстановление подтверждено владельцем. Клиент в этих ответах отдельно не уточнялся. Позднее владелец уточнил, что проверка смены учебного года также уже выполнена; отдельные сведения о клиенте, сохранении года после рестарта и возврате исходного значения в этом уточнении не приведены. Живое изменение группы и сравнение со вторым профилем ещё не выполнены.

Проверка systemd дала `is-active=active`, первоначально `is-enabled=disabled`. После явного `systemctl enable` владелец подтвердил `is-enabled=enabled`: сервис работает и настроен на запуск при загрузке VDS. Фактическая перезагрузка VDS в этой проверке не выполнялась.

Затем владелец остановил только службу бота и проверил обычную ручную переписку с включённым OMEMO: сообщение управляющего аккаунта из Gajim доставлено аккаунту тестового Гуся, ручной ответ из клиента Гуся получен управляющим аккаунтом. Доставка подтверждена в обе стороны. После запуска службы `is-active` снова показал `active`.

Тот же сценарий отдельно повторён с управляющего аккаунта в Conversations 2.20.4+free m149 на Android. При остановленной службе сообщение с телефона доставлено клиенту тестового Гуся, ручной ответ получен на телефоне. Владелец подтвердил обмен в обе стороны и `is-active=active` после повторного запуска службы. Остановка бота оставляет ручную переписку доступной в обоих проверенных клиентах; перезагрузка VDS не выполнялась.

В сценарии с работающей службой и отключёнными остальными клиентами аккаунта тестового Гуся владелец отправил из Gajim зашифрованный `!ping` и подтвердил ровно один ответ `Га-Га-Га!`. В присланном журнале есть `message_received source=direct`, затем `reply_queued`; исходящие `sent-carbon`, собственное сообщение и квитанция отброшены. Подтверждены прямая доставка в сервис и однократный ответ для этого обмена. Этот сценарий не подтверждает приём входящего `received-carbon` или доставку на явно заданный full JID.

Живой приём входящего `received-carbon`, доставка на full JID, восстановление после обрыва и остальные сценарии таблицы ещё не приняты.

Для профиля выполните от владельца `!admin user show pupil1@example.org`, затем `!admin user set pupil1@example.org grade=3`, отдельно год и `schedule_class_id`. Подставляйте только тестовый JID. После перезапуска сравните значения и второй профиль. Повторите команду от неадминистратора и от неизвестного отправителя. Ошибка не должна менять данные.

Для маршрутизации подключите сервис и оба клиента под тестовым JID Гуся с разными resource. Из существующего чата отдельного управляющего аккаунта отправьте зашифрованный `!ping` на bare JID. В журнале сервиса ожидается `message_received source=direct` или `source=received-carbon`, затем `reply_queued`; в управляющем клиенте — один расшифрованный ответ `Га-Га-Га!`. Наличие `reply_queued` само по себе не подтверждает получение. Отдельно повторите проверку, оставив онлайн только сервис: его приоритет `0` допускает bare-доставку. Если ответа нет, сохраните технические коды причин без содержимого сообщений и проверьте доверие устройств.

Затем проверьте доставку на full JID подключённых ресурсов, задавая адрес средствами клиента. Если диалог создания чата отклоняет адрес ещё при discovery, зафиксируйте это отдельно от доставки сообщения: такая ошибка не доказывает отсутствие XMPP-соединения сервиса. Входящая Carbon-копия проходит те же проверки отправителя и OMEMO, что прямая доставка. Их повтор не должен давать второй ответ; исходящие `sent`, ручные сообщения с ресурса Гуся, собственные ответы, архивные и delayed-копии не должны запускать цепочку ответов.

Для переподключения отключите сеть только тестового сервиса, затем восстановите её. Создайте диагностические сообщения во время отсутствия сервиса; проверьте поведение offline/delayed, архива и повторов. Архив не запускает команды, новое сообщение с новым ID после восстановления обрабатывается. Если исчерпан лимит попыток, выполните явный рестарт. Старый архив до добавления устройства бота может быть нерасшифровываемым — это не обещанная возможность.

## Техническое состояние и отчёт

```bash
sudo systemctl show goose-xmpp-bot.service \
  -p ActiveState -p SubState -p MainPID -p MemoryCurrent -p CPUUsageNSec
sudo journalctl -u goose-xmpp-bot.service -n 50 --no-pager
sudo du -h /var/lib/goose-xmpp-bot/goose.sqlite3
```

Размер БД и нагрузку измеряют после фактического теста. Не публикуйте конфиг, env, SQLite, содержимое сообщений, полные JID и ключи. В отчёте оставьте версии, коды причин, обезличенные шаги и ожидаемое/фактическое поведение. Любая несовместимость фиксируется с версиями и namespace; TLS/OMEMO не отключаются для её обхода.

Полная приёмка первого этапа требует живого прохождения обоих клиентов. Основной аккаунт и автоответы детям остаются отдельной задачей.
