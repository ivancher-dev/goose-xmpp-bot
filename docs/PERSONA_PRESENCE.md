# Гусь 0.3.2: истории, статус набора и лайки

[Задание](tasks/03a-persona-presence.md). Расширение поверх 0.3.1:
схема SQLite остаётся 4, зависимости и OMEMO-ключи сохраняются.

## Что меняется

Образ расширен историями Императора Вселенной, прожившего тысячелетия.
Гусь рассказывает от первого лица и чередует путешествия разных эпох,
домашние переоткрытия и дела Гусинландии. В истории есть задача, решение
и верное объяснение механизма. Ссылка на летописи больше не обязательный зачин.

Один ответ содержит один ход. Настоящий автор появляется после **нового
вопроса об авторстве**. Уточнение механизма само по себе его не раскрывает.
По просьбе без шуток и в фактической учебной справке Гусь сразу даёт факты.
Это инструкция модели; качество двух ходов нужно проверить на живом API.

При включении `typing_enabled` сервис отправляет XEP-0085 composing во время
подготовки ответа модели и active после окончания, ошибки или отмены.
Статус согласуется с клиентом по его уведомлениям состояния. С исправлением
0.3.3 учитываются также отдельные живые уведомления: подтверждение хранится
до пяти минут отдельно для каждого полного JID, не более восьми устройств
собеседника. Само уведомление не запускает ответ: нужен доверенный OMEMO-вопрос.
Если нет ни расширения во входящем вопросе, ни недавнего отдельного уведомления
этого устройства, статусы не отправляются.
Индикатор и его завершение адресуются устройству, приславшему вопрос;
адрес фиксируется в задании, чтобы другой клиент того же аккаунта его не подменил.
Режимы, профили, история и очередь по-прежнему разделяются по bare JID.
Уведомления не повторяются без смены состояния. Отображение и название
индикатора определяет приложение.
При сетевом обрыве исчезновение индикатора зависит также от таймаута клиента.

При `reactions_enabled` модель может отметить интересный вопрос в **том же
API-запросе**. Приложение убирает внутреннюю метку и отправляет 👍 как реакцию
XEP-0444 на origin-id, а при его отсутствии — на id входящего сообщения.
Нет подходящего ID — нет реакции. Решение поставить лайк необязательно.
Ограничение каждого диалога в текущей сессии: не чаще одного лайка за пять
вопросов модели и пять минут. Команды, manual, архив и повторы лайков не создают.

Текст ответа остаётся OMEMO. Состояния чата и реакции — отдельные служебные
XMPP-метаданные, не содержат текст вопроса. Чистые статусы и реакции, в том
числе реакции с fallback-body, не запускают команды и не включают manual.

## Обновление существующего сервиса

В чате владельца обновление проводится по одному шагу. Полный порядок для
самостоятельного повторения:

1. В чистом checkout загрузить выбранный SHA ветки `feat/goose-presence-and-persona`.
   [Порядок выбора и защищённой копии](INSTALLATION_STAGE3.md). Копия нужна
   свежая, после остановки **только сервиса Гуся**; ожидается схема 4.
2. Переключиться на выбранный SHA и выполнить `sudo bash scripts/install.sh`.
   Ожидается версия 0.3.2, схема 4, успешный локальный doctor. Конфиг, env,
   внешний образ и ключи сохраняются. Сервис установщик не запускает.
3. В существующем `/etc/goose-xmpp-bot/config.toml` добавить одну таблицу:

```toml
[interaction]
typing_enabled = true
reactions_enabled = true
```

В существующей таблице `[memory]` поменять `context_token_budget` на `9000`.
Не добавлять вторую таблицу `[memory]`. Это оценка по UTF-8 байтам с запасом:
расширенному образу нужно место для первого рассказа и следующего вопроса.
Число API-запросов из-за лайков не увеличивается; новые правила входят в
общий лимит контекста. Ограничения частоты и длины ответов остаются прежними.
Без `[interaction]` обе функции выключены — старый конфиг совместим.

4. Обновить **только раздел об изобретениях**, сохранив остальной образ:

```bash
cd /root/goose-xmpp-bot
sudo python3 scripts/update-persona-inventions.py \
  /etc/goose-xmpp-bot/persona.md --check
sudo python3 scripts/update-persona-inventions.py \
  /etc/goose-xmpp-bot/persona.md
```

Скрипт требует прежний заголовок «Рассказ об изобретении — два хода.» и границу
«Отвечай по-русски». Если структура другая, останавливается без замены.
Он создаёт полную копию `persona.md.before-inventions.*` с правами 0600,
сохраняет владельца, группу и права активного файла, остальные разделы и
параллельную правку другого редактора. Повторный запуск не меняет готовый файл.
Для нестандартного `llm.persona_file` указать именно настроенный путь.

5. Проверить и запустить:

```bash
sudo -u goose-xmpp-bot /opt/goose-xmpp-bot/venv/bin/goose-bot doctor \
  --config /etc/goose-xmpp-bot/config.toml
sudo systemctl start goose-xmpp-bot.service
```

Ожидаются active, успешное чтение MAM и `xmpp_ready`. Прежний подтверждённый
auto восстанавливается по правилам этапа 3; при ошибке архива нужна диагностика.
Непереданные текущему процессу doctor секреты не означают потерю EnvironmentFile.
В начале приёмки уточнить нужный диалог командой просмотра `!admin mode <bare_jid>`.

## Проверки для повторения по одному сценарию

1. Запросить развёрнутое объяснение в auto и проверить служебный индикатор,
   затем его исчезновение после ответа. Если индикатора нет, проверить
   настройки передачи состояний чата в используемом клиенте.
2. Во время подготовки ответа включить manual или отправить ручную реплику
   из обычного клиента Гуся. Ожидается прекращение индикатора без запоздалого
   ответа или лайка. Другой разрешённый диалог продолжает работать.
3. Включить auto и задать вопрос с собственной попыткой рассуждения.
   Лайк возможен, но не обязателен. Проверить привязку к нужному сообщению,
   отсутствие меток в тексте и отсутствие частых повторов. Команда `!ping`
   и повторная доставка не должны создавать лайк.
4. После очистки только своего тестового контекста задать «Как ты изобрёл
   застёжку-липучку?». Очистка удаляет память приложения этого диалога.
   Первый ответ — история Гуся с верным механизмом и без реального автора.
   Затем **новым сообщением** спросить «Точно ты?»; ожидается Жорж де Местраль
   с признанием его первенства. Отдельно проверить просьбу «без шуток».
5. После перезапуска проверить, что MAM с реакциями не переводит auto в manual
   и не возвращает метки в память. Повторить UI-проверки отдельно в каждом клиенте.

## Автоматические проверки и ограничения

Общий прогон 28 октября: **435 тестов прошли** (49 новых), 252 предупреждения
DeprecationWarning из slixmpp-omemo. Прошли `pip check`, компиляция Python,
`bash -n`, ссылки документации, TOML-примеры и `git diff --check`.
Тесты используют настоящие XML-плагины Slixmpp 1.17.0 и сериализуют исходящие
stanza, но подставляют сеть, PEP и ответы модели. Они проверяют отмену при API
и шифровании, старый финализатор, лимиты и независимость лайков, origin-id,
direct/Carbons/MAM, настройки клиента, отсутствие открытого текста и сохранение
остальных частей образа. Проверки качества реальной модели без API не выполнялись.

Из чистого коммита проверено настоящее обновление установленного wheel
0.3.1 → 0.3.2 через `install.sh --local` в отдельном каталоге. До явной смены
настроек конфиг, env, пользовательский образ и вся база схемы 4 сохранились
побайтно по SHA-256. Проверены прежние профиль, auto, история, город,
синтетическая запись OMEMO, дедупликация и подтверждённый курсор MAM.
Установленный пакет подтвердил CLI 0.3.2, doctor и `pip check`.

После явного включения новых настроек в том же каталоге отдельно проверены
скрипт обновления раздела (с полной копией и сохранением пользовательских
приписок), чтение нового образа и настоящий сериализатор статусов/реакции из
установленного wheel. Сеть XMPP и настоящий API не использовались.

Ограничения: счётчики редкости в памяти процесса, UI зависит от клиента,
соблюдение рассказа в два хода зависит от модели и её текущего контекста.
После выхода из состояния набора отправленный текст не отзывается.

Источники: [XEP-0085](https://xmpp.org/extensions/xep-0085.html),
[XEP-0444](https://xmpp.org/extensions/xep-0444.html). Правила сверены с XML
XSF и исходниками установленных плагинов Slixmpp, включая origin-id для личного
чата и запрет повторяющегося standalone composing без смены состояния.

## Исправление индикатора для нескольких устройств, 29 октября

После успешного обновления на 0.3.3 владелец сообщил, что Conversations
не показывает набор даже при долгом ответе. На скриншоте подтверждено,
что «Приватность → Оповещения о наборе» включены. Прежняя реализация
отправляла состояния на bare JID и учитывала согласование только внутри
текстового сообщения. Это не гарантировало доставку индикатора телефону
при одновременно подключённом настольном клиенте.

Исправление направляет composing/active на полный JID источника вопроса
и принимает отдельное согласование напрямую или через проверенный received
Carbon. Архив, задержка, sent Carbon, чужой отправитель/получатель, вложенные
оболочки и неизвестные состояния не открывают такое согласование. Эти события
не меняют manual/auto, не создают память, команды, лайки или API-запросы.
Кэш ресурсов существует только в памяти процесса.

Задание запоминает адрес и согласование до постановки в очередь. Поэтому
следующий вопрос из Gajim не перенаправляет уже ожидающий индикатор телефона;
конечный active уходит туда же, куда ушёл composing. Отмена и shutdown
по-прежнему завершают набор, а старый финализатор не завершает новое задание.
OMEMO-ответы и реакции сохраняют прежний адрес аккаунта и обработку.

Общий офлайн-прогон с исправлением: **495 тестов прошли**, 292 upstream
DeprecationWarning из slixmpp-omemo. Новые проверки включают два клиента
одного аккаунта в очереди, отдельные уведомления, direct/Carbons, TTL/лимит
ресурсов, запрет подмены другого устройства и сохранение проверки доверия.
Отдельно собран wheel 0.3.3 без сети, установлен в изолированный каталог;
именно из установленного пакета прошли все 60 проверок `test_social.py`.
В журнал добавлены только `chatstate_negotiated supported=… resource=…` и
`chatstate_sent state=…`: булевы признаки и фиксированное имя состояния,
без JID, resource, XML или текстов. Искусственная задержка ответа не добавлена.

Установка исправления выполняется зарегистрированным `goose-update --ref SHA`
с проверенным коммитом. На VDS после этого нужен новый вопрос именно из
Conversations с наблюдением индикатора и его исчезновения; затем та же проверка
из Gajim при подключённом телефоне. Живой успех исправления пока не заявляется.
